# 🐋 Dart · DeepSeek Harness（ddsh）

> 一个运行在安卓 Termux 环境上的、零第三方依赖的全栈 AI 工作台。
> 后端使用纯 Dart 从零实现，前端使用原生 HTML、CSS、JavaScript 构建，
> 同时打通 DeepSeek 官方接口与字节跳动火山引擎方舟（豆包）全家桶，
> 把对话、推理、联网检索、图片生成、视频生成、语音合成、语音识别、
> 实时全双工语音、角色扮演、论坛、单词本、文件管理、自动化操作、
> 峰谷电价提醒、数据备份等能力整合进同一个可长期运行的本地服务。

# 第一章 项目简介与设计哲学

## 1.1 这是一个什么样的项目

Dart · DeepSeek Harness，工程内部简称 ddsh，是一个把原本运行在服务器、
个人电脑上的大模型工作台，完整移植到安卓手机 Termux 环境中的项目。
它的前身是一个使用 Go 语言编写的同名工具，当前版本已经用 Dart 语言
做了百分之百的重写，并且刻意不引入任何第三方依赖包。

这句话里有几个关键词，需要逐一解释清楚，因为它们决定了整个项目的性格。

第一个关键词是「安卓 Termux」。Termux 是一个可以在安卓系统上运行的
终端模拟器与 Linux 环境应用，它不需要 root 权限，就能在手机里提供一个
接近完整的命令行环境。很多人以为手机只能用来消费内容，ddsh 却证明了
一台普通的安卓手机完全可以充当一台全天候在线的小型服务器，承载一个
功能完整的 AI 工作台。

第二个关键词是「零第三方依赖」。打开项目的 pubspec.yaml 文件可以看到，
dependencies 与 dev_dependencies 两个段落都是空的。这意味着项目没有
依赖 pub.dev 上的任何外部包。HTTP 服务直接使用 Dart 标准库的 dart:io，
AES-256-GCM 加密、SHA-256 摘要、HMAC 签名、tar.gz 打包，全部在仓库内部
用纯 Dart 手写实现。这样做的最大好处是：只要手机上装了 Dart SDK，
执行一条 dart run bin/main.dart 就能把整个服务跑起来，不需要联网拉取
依赖，也不用担心某个第三方包停更或者投毒。

第三个关键词是「全栈」。ddsh 不是一个单纯的命令行脚本，它既包含后端
HTTP 服务、业务逻辑、数据存储，也包含一整套可以直接在浏览器里打开的
前端界面。后端负责对接各家大模型接口、管理会话、调度工具、落盘数据；
前端负责渲染对话气泡、模型选择器、图片视频面板、论坛、单词本等交互。
两端通过同一台手机上的 HTTP 端口通信，形成一个闭环。

第四个关键词是「双引擎」。项目同时支持 DeepSeek 官方接口与火山引擎
方舟（豆包）接口，两套通道并列存在、互不影响。DeepSeek 通道擅长
通用对话、深度推理、工具调用与联网搜索；豆包通道则提供了更丰富的
多模态能力，包括图片生成、图片编辑、视频生成、语音合成、语音识别、
实时语音对话等。用户可以在界面上一键切换，也可以让系统根据附件类型
自动路由到最合适的模型。

## 1.2 为什么要用 Dart 重写

项目最早的 Go 版本已经具备了完整功能，之所以还要投入大量精力用 Dart
重写，主要基于以下几个现实考量。

第一，Termux 上的 Dart 运行体验更好。Dart 支持 JIT 直接运行，也支持
AOT 编译成原生可执行文件。开发阶段用 dart run 可以快速迭代，上线阶段
用 dart compile exe 可以生成一个不依赖 SDK 的独立二进制，兼顾了开发
效率与运行性能。

第二，单一语言贯穿前后端的心智负担更低。虽然前端仍然使用原生 JavaScript，
但后端业务逻辑全部集中在 Dart 中，数据结构、转义规则、时间格式、
加密算法都可以在同一套语言体系内对齐，减少了跨语言移植时容易出现的
细微偏差。

第三，零依赖策略在 Dart 上更容易贯彻。Dart 标准库本身提供了足够强大的
异步 IO、编码解码、加密原语支撑，使得手写 AES、SHA、tar 等基础组件
的成本可控。项目里的 aes_gcm.dart、sha256.dart 就是这种策略的产物。

第四，与 Go 版本保持逐字节兼容。重写并不是推倒重来，而是严格对齐
Go 版本的存储格式、转义规则、接口路径。例如 .sts 会话文件的转义函数
escDs 与 unescDs，在 Dart 版本里被要求与 Go 版本逐字节等价，从而保证
历史数据可以百分之百迁移，老用户升级后不会丢失任何会话。

## 1.3 核心设计哲学

整个项目在长期演进中沉淀出几条清晰的设计哲学，理解这些哲学有助于你
在二次开发时做出与项目风格一致的决策。

### 1.3.1 数据本地化，用户掌握所有权

所有会话、配置、附件、论坛帖子、单词本、角色扮演卡片，都以明文或
加密文件的形式保存在手机本地的 data 目录下，不依赖任何云端数据库。
用户可以随时通过备份功能把整个数据目录打包成 tar.gz 下载，也可以
在新设备上恢复。这种设计把数据所有权完全交还给用户，避免了厂商锁定，
也让离线运行成为可能。

### 1.3.2 接口对齐，行为可预期

项目大量模块的注释里都写着「100% 对齐 Go 版」。这不是一句口号，而是
一种工程纪律：文件路径、命名规则、转义字符、时间戳格式、HTTP 路由，
都尽量保持稳定。稳定的接口行为意味着前端、后端、备份文件、历史数据
之间的契约不会被随意破坏，长期运行的服务才值得信赖。

### 1.3.3 异常不杀进程，服务永远在线

在 main.dart 的入口处，整个服务被包裹在 runZonedGuarded 中。任何
未捕获的异步异常都只会被记录到日志，而不会让进程以非零退出码崩溃。
这背后是一个非常现实的教训：在长连接 SSE 场景下，一次普通的流写入
失败（例如浏览器突然关闭导致 StreamSink 异常），如果不被兜住，就会
杀死整个服务。对于一个希望全天候运行在手机上的工作台来说，「永远在线」
比「严格失败」更重要。

### 1.3.4 能力可组合，模块高内聚

项目把不同能力拆分成独立的 Dart 文件：对话是对话，加密是加密，
论坛是论坛，单词本是单词本，峰谷提醒是峰谷提醒。每个模块只负责自己的
领域，通过统一的 HTTP 路由对外暴露。这种高内聚、低耦合的组织方式，
让新增一个功能（例如接入一种新的信源）只需要改动局部文件，不会牵连
整个代码库。

### 1.3.5 真实优先，拒绝编造

项目在处理 Token 用量、模型能力、接口限制等敏感信息时，反复强调
「绝不估算」「全部为实测结论」。例如 ds_usage.dart 的注释明确要求
每条回复的 Token 用量必须采用服务商账单口径的真实值，而不是本地猜测。
这种诚实的工程态度，贯穿在模型目录、视频大小限制、信源互斥规则等
方方面面，也是本 README 撰写时严格遵守的原则：只描述代码里真实存在的
功能，不虚构任何不存在的特性。

## 1.4 适合哪些人使用

ddsh 的目标用户并不是泛泛的「所有想用 AI 的人」，而是有一定动手能力、
希望把 AI 能力牢牢掌握在自己手里的群体，典型包括：

- 希望在手机上搭建私人 AI 工作台、又不想把数据交给第三方云服务的玩家。
- 需要同时使用 DeepSeek 与豆包多模态能力、希望在一个界面里统一管理的
  内容创作者。
- 学习 Dart 后端开发、HTTP 服务、加密算法、SSE 流式通信的开发者，
  可以把本项目当作一个结构清晰的实战教材。
- 需要在安卓设备上做自动化操作、希望用自然语言驱动 ADB 指令的测试或
  运营人员。
- 对数据隐私敏感、要求所有历史会话可本地备份、可离线恢复的用户。

如果你完全不想接触任何配置、只想要一个开箱即用的商业 App，那么本项目
可能并不适合你；但如果你享受「自己掌控一台 AI 服务器」的乐趣，ddsh
会是一个非常趁手的工具。

## 1.5 项目当前规模

为了让你对项目体量有一个直观认识，这里给出基于当前代码库的真实统计。
后端 Dart 源码位于 lib/src 与 bin 目录，合计约两万六千多行；前端
JavaScript、HTML、CSS 合计约三万四千多行。后端最大的几个文件分别是
doubao.dart（豆包接入层，约两千七百行）、tools.dart（智能体工具集，
约两千五百行）、globals.dart（全局常量与工具函数，约两千行）、
peakvalley.dart（峰谷提醒，约一千七百行）、deepseek_api.dart（DeepSeek
调用层，约一千七百行）。前端最大的文件是 deepseek-chat.js（约六千
四百行）与 dsc-doubao.js（约两千七百行）。

这是一个经过长期迭代、功能密集的真实工程，而不是一个演示用的玩具。
后续章节会带你逐个拆解这些模块，让你不仅知道怎么用，还知道它为什么
这样设计。

# 第二章 核心特性全景

本章用一张全景图的方式，把 ddsh 目前真实具备的能力完整罗列出来。
所有特性都能在 lib/src 目录下的对应源码文件中找到实现，不存在任何
画饼式的功能描述。

## 2.1 DeepSeek 核心对话能力

DeepSeek 通道是整个项目的基石，承担通用对话、深度推理与工具调用的
主力职责。

### 2.1.1 流式对话与思考链展示

前端通过 SSE（Server-Sent Events，服务器发送事件）实时接收后端推送的
令牌，实现打字机效果。DeepSeek 推理模型返回的思考过程（reasoning）
会被单独解析并渲染成可折叠的「深度思考」区块，与正式回答区分展示。
chat_send.dart 与 deepseek_api.dart 共同负责这条流式链路，包括请求
发起、流读取、异常中断、落盘保存的完整生命周期。

### 2.1.2 会话与消息管理

sessions.dart 实现了基于单文件的会话存储。每一个会话对应 data 目录下
的一个 .sts 文件，内部记录会话元信息与全部消息。系统支持会话列表
加载、消息分页读取、会话批量删除、会话重命名、会话内容全文搜索。
search.dart 提供内存缓存加游标分页的全文检索能力，可以在大量历史
会话中快速定位关键词。

### 2.1.3 跨会话引用

session_ref.dart 实现了一个很有特色的能力：跨会话引用（mention）。
它定义了形如 dsh-session: 加 base64url 编码的统一资源标识符，允许
用户在一条新消息里引用另一个历史会话。后端解析该标识符后，会把被
引用会话的快照注入当前上下文，从而让模型在回答时能够参考历史讨论，
实现跨会话的记忆延续。

### 2.1.4 模型自动路由

model_router.dart 解决了一个真实痛点：当用户上传图片时，普通文本模型
无法理解图像内容。自动路由模块会检测附件类型，一旦发现图片，就把
请求自动切换到具备视觉能力的模型，处理完成后再恢复用户原本选择的
模型。整个过程对用户透明，不需要手动来回切换。

### 2.1.5 真实 Token 用量

ds_usage.dart 严格采用服务商返回的账单口径 Token 数据，在每条回复后
展示真实的输入、输出 Token 消耗，而不是在本地用字符数粗略估算。
这对于控制成本、核对账单非常关键。

### 2.1.6 中断保存与续写

当用户在生成过程中点下停止按钮时，abort-save 接口会优雅地中断 SSE
流，并把已经生成的部分内容完整保存下来，不会丢失。continue 接口则
支持在已有回答的基础上让模型继续往下写，适合长文创作场景。

## 2.2 豆包（火山方舟）全家桶

doubao.dart 是项目里体量最大的单文件，它对接的是字节跳动火山引擎
方舟平台的豆包系列模型。与 DeepSeek 通道相比，豆包通道的最大价值
在于多模态能力的广度。

### 2.2.1 文本对话

豆包通道同样支持流式文本对话，内置多个聊天模型，包括 Doubao-Seed
系列的 pro、turbo、lite、mini 等档位，以及一个 GLM 编码模型。
用户可以根据任务难度与成本预算灵活选择。

### 2.2.2 图片生成与编辑

项目接入了 Seedream 系列图像模型，支持文生图与图生图（图片编辑）。
doubao.dart 内置图片风格预置列表，例如动漫、二次元、日本动漫风、
像素、电影感、特摄风、中国动漫风、田野风等，用户选中风格后会自动
拼接到提示词中，同时也保留完全自定义提示词的自由。

### 2.2.3 视频生成与大视频理解

视频生成由 Seedance 系列模型承担，支持异步任务创建、状态轮询、
任务列表管理。更值得一提的是 doubao_video_ark.dart 实现的大视频
理解通道：45 兆字节以内的视频可以直接通过 video_url 上传，超过这个
大小、最高支持 2GB 的视频，则调用 ffmpeg 进行无损切片，分段理解后
再汇总结果，从而绕开单次请求的体积限制。

### 2.2.4 语音合成与语音识别

tts 接口对接 SeedAudio 语音合成模型，支持多音色，默认音色为
zh_female_xiaohe_uranus_bigtts，并提供一个备用男声。asr 接口对接
豆包录音文件识别与流式语音识别模型，可以把音频转写成文字。

### 2.2.5 播客与实时语音

podcast 接口支持生成双人对话式播客；realtime 与 rtc 系列接口则对接
豆包端到端实时语音（Seeduplex）与 RTC 音视频互动能力，实现全双工
语音对话，也就是可以随时打断、自然交谈的语音助手体验。

### 2.2.6 联网内容插件

doubao_wiki.dart 专门负责接入火山方舟的联网内容插件，支持抖音百科、
头条图文、墨迹天气、全网检索等信源。由于该插件只在 Responses API
下可用，普通 Chat Completions 接口无法指定这些信源，因此项目单独
实现了一条 Responses API 通道，这部分会在第十二章详细展开。

## 2.3 手机实操能力（工具模式）

tools.dart 是智能体的「双手」。它定义了九十多个工具的 JSON Schema
与具体执行逻辑，让模型不仅能说，还能动手操作真实设备。

这些工具覆盖了安卓自动化的方方面面：点击、长按、滑动、输入文字、
按键事件、截图、屏幕尺寸查询、界面元素查找、应用启动与强制停止、
剪贴板读写、音量调节、亮度控制、手电筒、拍照、传感器读取、定位、
WiFi 管理、通知与 Toast、震动、TTS 朗读、短信与通讯录、通话记录、
应用安装卸载与权限管理、系统设置读写等。

工具模式支持多轮循环与反思：模型调用一个工具后拿到执行结果，可以
根据结果决定下一步动作，形成「感知、决策、执行、再感知」的闭环。
doubao_tools.dart 则为豆包通道提供了并列的工具模式实现，两套工具
体系互不干扰。

## 2.4 附加生态模块

除了核心对话与多模态，项目还内置了一组完整的生态模块，让它从一个
聊天界面升级为一个综合性工作台。

### 2.4.1 角色扮演（Cosplay）

cosplay.dart 实现了角色卡片系统，数据存放在 data/cosplay 目录。
用户可以创建、编辑、切换不同的人格角色，每个角色包含身份设定、
性格、说话风格、行为准则、开场白、对话示例等字段，兼容主流角色卡
格式。

### 2.4.2 论坛系统

forum.dart 提供轻量级论坛能力，帖子以一帖一文件的形式存放在
data/dispost 目录，支持发帖、详情查看、点赞等互动、删除与清空。
前端 dsc-forum.js 负责渲染帖子流与交互。

### 2.4.3 公告系统

announcements.dart 实现了带生效时间区间、优先级、强制置顶能力的
公告系统，管理员可以发布在指定时间段内对用户展示的通知。

### 2.4.4 日语单词本

vocab.dart 是一个颇具特色的学习工具，采用首字分片存储加二百五十六
个图片分桶的设计，支持单词录入、复习、图片关联、清空等操作，前端
dsc-vocab.js 提供完整的学习界面。

### 2.4.5 文件管理

files.dart 实现了分片上传、下载、列表、删除、清空的完整文件管理
能力，元数据按月归档到 data/ds_files/meta 目录，二进制内容存放在
blob 与 chunks 目录，支持超大文件的可靠传输。

### 2.4.6 峰谷电价提醒

peakvalley.dart 对接 DeepSeek 官方峰谷定价时段，实现阶段判定、时段
换算、模板渲染、七种推送渠道与服务端定时调度，帮助用户在便宜时段
集中跑任务、在昂贵时段节制调用。

### 2.4.7 X 推文抓取

xtweet.dart 通过多后端并发竞速的方式高速抓取 X（原 Twitter）推文，
只要任意一个后端率先返回结果就立即采用，兼顾速度与可用性。

### 2.4.8 Edge TTS 与 DRM 签名

tts_edge.dart 通过 WebSocket 对接微软 Edge 浏览器的免费 TTS 服务，
输出 24kHz、48kbps 的单声道 MP3。tts_drm.dart 则纯 Dart 实现了
微软要求的 Sec-MS-GEC 第二版签名，包含 CS64 与 SHA256 双摘要，
保证在 DRM 升级后依然可以正常合成语音。

# 第三章 技术栈与零依赖说明

## 3.1 后端技术栈

后端完全使用 Dart 语言编写，最低支持 Dart 3.0 SDK。选择 Dart 的原因
在第一章已经说明，这里聚焦它在本项目里具体承担的职责。

dart:io 是整个后端最核心的标准库，HttpServer、HttpClient、WebSocket、
文件系统、进程管理、Socket 通信全部由它提供。项目没有使用任何 Web
框架，路由分发、中间件、静态资源服务都是手写的。httpsrv.dart 负责
HTTP 服务的搭建，包括精确路由匹配、前缀路由匹配、CORS 中间件、
日志中间件、静态文件服务与 index.html 回退。

dart:convert 提供 JSON、UTF-8、Base64 等编解码能力，是接口数据交换
的基础。dart:async 提供 Future、Stream、Zone 等异步抽象，支撑 SSE
流式推送与全局异常兜底。dart:math 提供随机数与数学计算，用于生成
随机标识、图片尺寸对齐等场景。

## 3.2 零依赖的底气与代价

pubspec.yaml 里 dependencies 与 dev_dependencies 均为空，这是一个
经过深思熟虑的决定，既有明显收益，也有真实代价，值得客观说明。

收益方面，第一是部署极简。克隆代码后只要有 Dart SDK 就能运行，
不需要执行 pub get，不存在依赖解析失败、版本冲突、网络受限导致装不上
包的问题，这在 Termux 这种网络环境不稳定的场景下尤其重要。

第二是供应链安全。近几年开源投毒事件频发，依赖越多，攻击面越大。
零依赖意味着项目的全部代码都在自己仓库里，安全审计只需要审查自身
代码，不用为成百上千个间接依赖的安全性背书。

第三是长期可维护。第三方包可能停更、可能改协议、可能引入破坏性变更，
而标准库的稳定性极高。把核心能力握在自己手里，项目的生命周期不再
受制于外部维护者。

代价方面，第一是开发量更大。AES-256-GCM、SHA-256、HMAC、tar 打包、
DRM 签名这些本来可以靠现成库解决的问题，都需要自己手写并充分测试。
第二是对开发者要求更高，需要理解加密、编码、网络协议的底层细节。
第三是某些高级特性需要持续跟进外部协议变化，例如 Edge TTS 的 DRM
从第一版升级到第二版时，tts_drm.dart 就必须同步实现新的签名算法。

综合来看，对于一个追求长期稳定运行、部署环境受限、对数据安全敏感的
个人工作台，零依赖的收益明显大于代价，这也是项目始终坚持这一原则的
根本原因。

## 3.3 前端技术栈

前端没有使用 React、Vue 等任何框架，也没有打包构建步骤，全部是浏览器
原生能力。

HTML 入口是 index.html，约九百行，负责整体页面骨架与静态资源引用。
样式分散在多个 CSS 文件中：deepseek-chat.css 是主界面样式，
dsc-doubao.css 负责豆包面板，ds-files.css、ds-devtools.css、
peakvalley.css、dsc-forum.css、dsc-vocab.css 分别对应各自模块。

JavaScript 采用多文件按职责拆分的组织方式。deepseek-chat.js 是体量
最大的前端文件，承担主对话逻辑；dsc-doubao.js 负责豆包多模态面板；
peakvalley.js 负责峰谷提醒；dsc-forum.js、dsc-vocab.js、ds-files.js、
ds-devtools.js 分别对应论坛、单词本、文件、开发者工具。还有一批
小型增强脚本：dsc-swipe.js 处理滑动手势，dsc-menu-scroll.js 处理菜单
滚动，dsc-newline-fx.js 处理换行特效，dsc-model-route.js 处理前端
模型路由，dsc-ja-fix.js 修复日语显示细节，dsc-duplex.js 处理全双工
语音，dsc-announcements.js 处理公告弹窗。

这种无框架、无构建的方案带来的好处是：任何静态文件服务器都能直接
托管，浏览器打开即用，调试时可以直接在 Sources 面板里打断点，不存在
源码映射的黑盒。

## 3.4 国际化方案

i18n 目录承载整套多语言体系。i18n.js 是翻译引擎，locales 目录下按
语言存放字典文件，目前支持日语、中文、英语、韩语、俄语、法语六种
语言，每种语言又分为主字典与 extra 补充字典两个文件。

项目以日语字符串作为翻译键，这与它最初面向日语用户的历史有关。
界面上的文案先以日语写出，再在各语言字典里建立日语到目标语言的
映射。ai-prompts.js 则存放不同语言下的系统提示词，让模型能够用用户
选择的语言进行回复。第十二章会进一步分析这套机制的工程细节。

## 3.5 数据存储方案

项目没有引入 SQLite 或任何数据库引擎，而是采用文件系统作为唯一存储。
不同类型的数据有各自的目录与文件格式约定。

会话、配置、论坛帖子、公告、单词本、角色扮演状态等结构化数据，普遍
采用 .sts 文本格式。这是项目自定义的一种轻量格式，通过特定的头行与
内容行、竖线分隔符与转义规则来表达结构，兼顾人类可读性与机器解析
效率。需要加密的敏感配置（例如 DeepSeek 配置、主密钥相关数据）则
先经过 AES-256-GCM 加密再落盘。

文件上传的二进制内容采用分片目录管理，峰谷提醒等模块使用少量 JSON
文件。整体上，data 目录就是整个应用的数据库，备份时只需打包这一个
目录即可完成全量备份，恢复时解压回去就能原样运行，这是文件存储相对
数据库最直观的运维优势。

# 第四章 目录结构与文件职责

理解一个工程最快的方式，是先看懂它的目录结构。本章按照「根目录、
后端源码、前端资源、数据目录、国际化目录」五个层次，把项目里每一个
重要文件的职责讲清楚。

## 4.1 根目录总览

项目根目录位于 Termux 用户主目录下的 ddsh 文件夹，绝对路径为
/data/data/com.termux/files/home/ddsh。根目录下混合存放着后端入口、
前端静态资源、自动化脚本与工程配置。

pubspec.yaml 是 Dart 工程的描述文件，声明工程名 ddsh、版本号、SDK
约束，以及最关键的一点：没有任何第三方依赖。pubspec.lock 是锁定文件，
由于没有依赖，它的内容非常精简。

bin/main.dart 是后端程序的唯一入口，负责加载环境变量、初始化数据
目录、注册全部路由、启动 HTTP 服务，并通过 runZonedGuarded 兜底所有
未捕获异常。

app 是 AOT 编译产出的原生可执行文件，可以在不安装 Dart SDK 的环境
直接运行。README.md 就是你正在阅读的这份文档。.gitignore 声明了
Git 版本管理需要忽略的文件与目录，例如编译产物、临时文件、敏感数据。

## 4.2 自动化脚本

根目录下有三个 Python 脚本与一个 Shell 脚本，它们共同构成安卓自动化
与辅助运维能力。

adb_up.sh 负责建立并维持 ADB（安卓调试桥）连接。它会启动一个脱离
终端生命周期的 ADB 服务进程，连接本机的无线调试端口，校验连接身份，
确保后续自动化指令有可用的通道。在设备重启或者 ADB 掉线之后，重新
执行一次这个脚本即可恢复。

auto.py 是安卓全自动操作引擎，封装了点击、滑动、输入、截图、OCR、
应用启动等一系列高层操作，可以被智能体工具模式调用，也可以独立运行
完成固定流程。doubao_auto.py 则是面向豆包相关流程的自动化脚本。
ha.py 与 st.py 提供额外的辅助能力，配合主引擎完成特定场景的自动化。

## 4.3 后端源码目录 lib/src

lib/src 是后端业务逻辑的核心，所有 Dart 模块都集中在这里。下面按照
功能域分组说明。

### 4.3.1 基础设施层

globals.dart 是全局基础设施，定义基础路径、数据目录、端口、上传大小
上限、日志函数、随机标识生成、.sts 转义与反转义、时间格式化等通用
工具。几乎所有其他模块都依赖它。

net.dart 提供共享的 HttpClient，内置连接池复用与自动代理探测逻辑，
统一管理出站 HTTP 请求，避免每次请求都新建连接带来的开销。

httpsrv.dart 实现 HTTP 服务器本体，包括路由表、前缀路由、CORS 跨域
中间件、访问日志中间件、静态资源服务与单页应用回退。

sha256.dart 是纯 Dart 实现的 SHA-256 与 HMAC-SHA256，主要用于钉钉、
飞书机器人的加签。aes_gcm.dart 是纯 Dart 实现的 AES-256-GCM 对称
加密。ds_crypto.dart 在二者之上构建主密钥管理、配置加解密与 DeepSeek
配置读写能力。

### 4.3.2 DeepSeek 业务层

deepseek_api.dart 是 DeepSeek 接口调用层，覆盖非流式与流式对话、
工具模式多轮循环、多轮反思、视觉理解、联网搜索等。chat_send.dart
专注发送接口与 SSE 流式输出，还包含小说模式的长文生成逻辑。
chat_handlers.dart 承载配置、会话、消息、推理、测试、图片、语音等
基础聊天接口的请求处理函数。

sessions.dart 管理会话与消息的 .sts 单文件存储。session_ref.dart
处理跨会话引用的解析与快照注入。search.dart 提供会话全文搜索。
model_router.dart 实现附件驱动的模型自动路由。ds_usage.dart 负责
真实 Token 用量统计。displaymodels.dart 管理用户自定义模型列表。
devtools.dart 提供开发者工具的提示词管理能力。

### 4.3.3 豆包业务层

doubao.dart 是豆包接入的总入口与模型目录，定义 DbConfig 配置结构、
DbModelSpec 模型规格、全部默认模型标识、多语言消息表，以及图片、
音频、视频等多模态消息体的构造函数。

doubao_intent.dart 实现前缀强制信源路由，识别「抖音百科搜索：」
「墨迹天气：」等触发词。doubao_wiki.dart 接入联网内容插件，走
Responses API 通道。doubao_tools.dart 提供豆包专属工具模式。
doubao_thinking.dart 优化深度思考输出的渲染。doubao_realtime.dart
对接端到端实时语音与 RTC。doubao_video_ark.dart 实现最高 2GB 的
大视频理解通道。

### 4.3.4 生态功能层

cosplay.dart 是角色扮演核心。forum.dart 是论坛。announcements.dart
是公告系统。vocab.dart 是日语单词本。files.dart 是文件分片上传
下载。backup.dart 是 tar.gz 备份与恢复。peakvalley.dart 是峰谷电价
提醒。xtweet.dart 是 X 推文高速抓取。tts_edge.dart 与 tts_drm.dart
共同实现 Edge 语音合成及其 DRM 签名。tools.dart 是九十多个智能体
工具的 Schema 与执行器。

## 4.4 前端静态资源

根目录直接存放前端资源，这是因为后端静态服务默认以根目录为站点根。

index.html 是唯一的页面入口。deepseek-chat.css 与 deepseek-chat.js
是主对话界面的样式与逻辑。dsc-doubao.css、dsc-doubao.js、
dsc-doubao-tools.js 构成豆包多模态面板。ds-files.css 与 ds-files.js
对应文件管理器，ds-devtools.css 与 ds-devtools.js 对应开发者工具。

peakvalley.css 与 peakvalley.js 对应峰谷提醒界面。dsc-forum.css 与
dsc-forum.js 对应论坛。dsc-vocab.css 与 dsc-vocab.js 对应单词本。
dsc-announcements.js 负责公告弹窗，dsc-duplex.js 负责全双工语音，
dsc-model-route.js 负责前端模型路由状态，dsc-swipe.js、
dsc-menu-scroll.js、dsc-newline-fx.js、dsc-ja-fix.js 提供手势、滚动、

tex-chtml-full-speech.js 是数学公式渲染相关的第三方运行库，用于在
对话中正确显示复杂公式。favicon.png 是站点图标，sw.png 是界面用到的
图片资源。

## 4.5 数据目录 data

data 目录是整个应用的状态中心，下面按子目录划分。

deepseek_chat 存放 DeepSeek 与豆包的核心数据，包括 ds_chat_config.sts

（路由规则）、ds_master.key（主密钥）、doubao_video_ark.json（视频

## 4.6 国际化目录 i18n

i18n/i18n.js 是翻译引擎。i18n/ai-prompts.js 存放多语言系统提示词。
i18n/locales 存放六种语言的字典，每种语言两个文件：主字典（如
zh.js）与补充字典（如 zh-extra.js）。补充字典主要承载后端 Dart 与
Python 报错文案的翻译，主字典承载界面静态文案与模型标签。

# 第五章 环境要求与安装部署

## 5.1 硬件与系统要求

ddsh 的目标运行环境是安卓设备上的 Termux。理论上任何能够正常运行
Termux 与 Dart SDK 的安卓设备都可以部署，实际体验则取决于设备性能。

内存方面，建议至少预留 2GB 可用内存。Dart VM 本身占用不高，但在
处理大视频切片、长上下文对话、并发 SSE 连接时，内存需求会明显上升。
存储空间方面，基础程序与静态资源不足百兆，但 data 目录会随着会话、
附件、视频、备份的积累持续增长，建议预留几个 GB 的空闲空间。

网络方面，设备需要能够访问 DeepSeek 与火山引擎方舟的接口端点。如果
处于需要代理才能访问的网络环境，可以通过环境变量配置出站代理，
具体方法见第二十七章。

## 5.2 安装 Termux 与 Dart

首先安装 Termux。建议从官方渠道获取，避免使用过时且来源不明的版本。
首次启动后先执行包管理器更新，升级全部已安装组件，保证环境处于最新
状态。

接着安装 Dart SDK。Termux 的包管理器提供 dart 包，安装完成后执行
dart --version 确认版本号满足 pubspec.yaml 声明的 SDK 约束，即
不低于 3.0 且低于 4.0。

如果还要使用大视频理解的切片能力，需要额外安装 ffmpeg。普通对话、
图片、语音功能不依赖它，只有当你计划处理超过 45MB 的视频时才必须
安装。

## 5.3 获取项目代码

把项目代码放到 Termux 用户主目录下的 ddsh 文件夹，保证绝对路径为
/data/data/com.termux/files/home/ddsh。这个路径不是随意选择的，
globals.dart 里的 BASE_DIR 默认就指向这里，大量模块也以它为基准
推导数据目录。如果你确实需要换位置，可以通过 DSH_BASE 环境变量
覆盖，但除非有充分理由，否则强烈建议沿用默认路径，避免不必要的
路径问题。

## 5.4 三种运行方式

项目提供三种运行方式，分别适配开发调试、日常使用与生产部署。

第一种是 JIT 直接运行，执行 dart run bin/main.dart。Dart 虚拟机
会即时编译并启动服务，修改代码后重启即可生效，适合开发与调试阶段。
这种方式不需要生成任何二进制文件，但要求设备上始终安装 Dart SDK。

第二种是 AOT 编译运行，执行 dart compile exe bin/main.dart -o app，
把程序编译成名为 app 的原生可执行文件，之后直接运行 ./app 即可。
AOT 编译后的程序启动更快、运行更稳定、不依赖 SDK，适合长期部署。
针对安卓平台还可以显式指定 --target-os=android 进行交叉优化。

第三种是借助自动化脚本运行。项目配套的脚本可以在前台运行、后台
守护运行、或者注册为 termux-services 服务之间切换。后台守护模式
会自动持有 Wake Lock 防止设备休眠，服务模式则支持崩溃自动拉起与
开机自启，适合追求全天候在线的用户。

## 5.5 服务启动与访问

服务默认监听 9999 端口，可以通过 DSH_PORT 环境变量修改。启动成功后，
在设备浏览器访问 http://127.0.0.1:9999 即可打开主界面。如果希望在
同一局域网的其他设备访问，需要监听合适的地址并注意防火墙设置，
Termux 环境下通常直接使用本机回环地址最安全。

首次启动时，程序会自动创建 data 目录及其全部子目录，不需要手动
建文件夹。如果 data 目录已经存在且包含历史数据，程序会原样读取，
实现无感升级。

## 5.6 静态检查与编译验证

在正式运行之前，建议先执行 dart analyze 做静态分析。它会检查语法
错误、类型问题与潜在缺陷，且只做分析、不产生编译产物。本项目在
每次改动后都要求通过静态检查，保证代码质量。

需要特别强调的是，本 README 涉及的文档撰写工作不会替你执行编译。
是否编译、何时编译、用什么参数编译，完全由你自己决定。文档只会
告诉你编译命令与适用场景，不会擅自生成或覆盖 app 二进制。

## 5.7 升级与回滚

升级时，用新代码覆盖旧代码，但务必保留 data 目录。由于存储格式
保持向后兼容，新版本可以直接读取旧数据。升级前建议先通过备份功能
下载一份完整 tar.gz，万一新版本不符合预期，可以回退代码后恢复备份，
把数据还原到升级前的状态。

这种「代码与数据分离」的设计，让升级与回滚都变成非常轻量的操作，
不需要做复杂的数据库迁移，这也是文件存储方案带来的长期运维红利。

# 第六章 快速开始与首次配置

本章带你从零开始，把一个刚部署好的 ddsh 服务配置到可以正常对话的
状态。整个过程不需要写代码，全部在浏览器界面里完成。

## 6.1 配置 DeepSeek API Key

打开主界面后，进入 DeepSeek 设置面板，填写你的 API Key。Key 会被
加密后写入 data/deepseek_chat/ds_chat_config.sts，而不是明文保存。
加密依赖主密钥 DS_MASTER_KEY，第二十一章会详细讲解它的生成与作用。

除了 Key，DeepSeek 配置还包括接口基础地址、默认模型、推理等级等
选项。绝大多数情况下保持默认基础地址即可，只有在使用兼容网关或
代理时才需要修改。填写完成后可以使用内置的测试接口验证 Key 是否
有效，测试请求会返回真实的连通性结果，避免把错误配置留到正式对话
时才暴露。

## 6.2 配置豆包 API Key

豆包配置的入口在豆包面板的设置区域，对应后端的 DbConfig 结构。
最核心的字段是 apiKey 与 baseUrl。baseUrl 默认指向火山引擎方舟的
官方端点 https://ark.cn-beijing.volces.com/api/v3，通常不需要修改。
apiKey 则填写你在方舟控制台获取的密钥。

DbConfig 还为每一类能力分别保存默认模型标识：chatModel 是对话模型，
imageModel 是图片生成模型，videoModel 是视频生成模型，ttsModel 是
语音合成模型，podcastModel 是播客模型，asrModel 是语音识别模型，
realtimeModel 是实时语音模型。这样细分的好处是每一种能力都可以
独立选择最合适、最划算的模型，而不是被迫用一个模型应付所有场景。

此外还有音色 voice 与备用音色 voiceB、水印开关 watermark、音频
自动路由 autoRouteAudio、快速模式 fastMode、自定义模型列表
customModels、联网信源列表 webSources、百科总开关 wikiEnabled，
以及实时语音与 RTC 所需的一组独立凭证。第九章会逐项解释这些字段
的含义与推荐取值。

## 6.3 主密钥的初始化

主密钥 DS_MASTER_KEY 是整个加密体系的根。它可以通过环境变量注入，
也可以写入 .env 文件。首次运行时，如果系统检测到还没有主密钥，
会引导生成一个 32 字节的随机密钥，以十六进制形式保存。

请务必妥善备份主密钥。所有加密配置都与它绑定，一旦丢失，已经加密
的配置将无法解密；一旦泄露，拿到 data 目录的人就可能解密你的敏感
信息。主密钥与数据目录应当分开保管，不要把它们放在同一个备份包里
明文传播。

## 6.4 界面语言切换

前端支持六种界面语言，切换后界面静态文案、模型标签、后端返回的
多语言提示都会跟随变化。由于后端豆包模块内置了六语言消息表，很多
错误提示直接由后端按当前语言返回，不依赖前端二次翻译，保证了提示
信息的准确与一致。

## 6.5 第一次对话

完成 Key 配置后，在输入框输入一条普通消息发送，观察是否出现流式
打字机效果。正常情况下，模型会逐字返回回答，回答结束后展示真实
Token 用量。如果开启了推理模型，还会看到可折叠的深度思考区块。

接着可以测试一次带附件的对话：上传一张图片，模型自动路由模块会
切换到视觉模型进行理解。再测试一次联网搜索，确认搜索信源工作正常。
当这几个基础链路都跑通，说明部署已经成功，后续就可以逐步探索图片
生成、视频、语音、角色扮演等高级能力。

## 6.6 常见首次配置问题

第一种常见问题是 Key 无效或余额不足。表现为接口返回鉴权失败或
计费错误，此时应回到对应平台控制台核对 Key 是否复制完整、账户是否
有可用额度。

第二种是网络不通。如果设备处于受限网络，需要配置代理环境变量，
并注意 dart:io 对 SOCKS 代理的支持限制，第二十七章会给出具体方案。

第三种是端口被占用。如果 9999 端口已经被其他程序占用，可以通过
DSH_PORT 换一个端口启动。

第四种是数据目录权限问题。Termux 环境下要保证运行用户对 ddsh 目录
拥有读写权限，尤其是 data 目录，否则会话无法落盘、配置无法保存。

# 第七章 DeepSeek 对话核心

DeepSeek 通道是 ddsh 的立身之本，本章深入讲解它的内部工作机制，
帮助你理解一次对话从发送到落盘究竟经历了什么。

## 7.1 一次请求的完整生命周期

当你在输入框敲下发送按钮，前端首先收集当前会话标识、消息内容、
附件、模型参数、推理等级等信息，组装成请求体，POST 到
/api/ds-chat/send 接口。

chat_send.dart 接到请求后，先做参数校验与附件预处理。如果存在
图片附件，model_router.dart 会判断当前模型是否具备视觉能力，必要时
临时切换模型。随后 deepseek_api.dart 构建符合 DeepSeek 接口规范的
请求，带上历史消息、系统提示词、工具定义等，发起调用。

如果是流式响应，后端会持续读取服务器返回的数据流，把思考过程与
正式内容通过 SSE 实时转发给前端。前端一边接收一边渲染，形成打字机
效果。流结束后，后端把完整的消息、思考链、Token 用量写入会话的
.sts 文件，完成持久化。

## 7.2 SSE 流式的工程细节

SSE 是一种基于 HTTP 长连接的服务器推送技术，相比轮询更省资源、
实时性更好。ddsh 的 SSE 实现需要处理几个棘手的工程问题。

其一是连接中断。用户可能随时关闭浏览器、切走应用、网络可能抖动。
后端在写入流时必须捕获这类异常，避免一次写入失败导致整个进程崩溃，
这正是 main.dart 用 runZonedGuarded 兜底的原因之一。

其二是主动停止。用户点击停止按钮时，前端调用 abort-save 接口，
后端优雅地终止上游连接，并把已经收到的部分内容保存下来，保证
不丢数据。

其三是思考与正文的分流。推理模型会把思考过程与最终回答放在不同
字段，后端需要准确区分并打上类型标记，前端才能把思考渲染成独立的
折叠区块，而不是混在正文里。

## 7.3 工具模式与多轮反思

普通对话只能「说」，工具模式让模型能够「做」。tools.dart 用 JSON
Schema 描述了九十多个工具，每个工具包含名称、功能描述、参数结构。
模型在回答时如果判断需要调用工具，会返回结构化的工具调用请求，
后端校验参数后执行真实操作，再把结果回传给模型。

这个过程可以循环多轮。例如用户说「帮我打开微信给某人发消息」，
模型可能先调用 ADB 连接工具确认通道，再调用启动应用工具打开微信，
接着调用输入工具搜索联系人，最后调用点击与输入工具完成发送。每一步
的结果都会反馈给模型，由它决定下一步，形成完整的自动化闭环。

多轮反思机制则让模型在拿到工具结果后能够自我检查。如果某一步失败，
模型可以根据错误信息调整策略、换一种方式重试，而不是直接把失败
抛给用户。deepseek_api.dart 里的工具循环逻辑负责驱动这一过程。

## 7.4 小说模式与长文生成

chat_send.dart 内置小说模式，专门服务长篇创作。普通对话受单次输出
长度限制，长文容易被截断。小说模式配合续写接口，把一部长篇拆成
多段连续生成，模型在每一段结束后自动接续，直到完成整体结构。

中断保存能力在这里同样关键。即使生成长篇时网络波动或用户主动停止，
已经写出的内容也会被保存，下次可以从断点继续，不会前功尽弃。

## 7.5 会话存储格式

sessions.dart 使用 .sts 单文件存储会话。这种格式通过转义规则把
可能产生歧义的字符保护起来：反斜杠转义为双反斜杠，竖线转义为
反斜杠加 p，换行转义为反斜杠加 n。globals.dart 里的 escDs 与
unescDs 负责这对可逆转换，并且针对长字符串做了性能优化，采用跳段
处理而非逐字符拼接，在处理数十万字符的长思考链时能明显降低开销。

选择单文件存储而不是数据库，是为了让每个会话都成为可以独立复制、
备份、检查的实体。你甚至可以直接用文本工具打开 .sts 文件查看原始
内容（加密配置除外），这种透明性是黑盒数据库无法提供的。

## 7.6 全文搜索

随着会话越积越多，快速找回历史内容成为刚需。search.dart 实现了
内存缓存加游标分页的全文搜索：首次搜索时扫描会话建立缓存，后续
搜索复用缓存提升速度，结果通过游标分页返回，避免一次性加载过多
数据卡住界面。

## 7.7 跨会话引用的价值

单一会话的上下文是有限的，而真实工作往往需要参考过去的讨论。
session_ref.dart 的跨会话引用机制，让你可以在新对话里通过特定
URI 引用旧会话，后端把旧会话快照注入当前上下文。这样模型就能基于
历史背景回答，而不需要你手动复制粘贴大段内容，显著提升了复杂、
长期任务的连贯性。

## 7.8 DeepSeek 通道的边界

客观说明 DeepSeek 通道的能力边界同样重要。根据项目内置的多语言
提示，DeepSeek 通道本身不负责音频与视频的内容理解。当你上传音频
或视频时，系统会明确提示该通道无法读取文件内容，并建议切换到
豆包模式、选择支持音视频理解的模型。这种诚实的能力声明，避免了
用户误以为文件已经被理解、实际上模型却在凭空猜测的危险情况。

# 第八章 豆包大模型选型推荐（重点）

本章面向正在犹豫「该选哪个大模型」的用户，结合 ddsh 项目里真实
接入的豆包模型目录，给出可落地的选型建议。所有模型标识都来自
doubao.dart 的 dbModelCatalog，是代码里真实存在、可以直接在界面
选择的模型，而不是凭空罗列的营销名单。

## 8.1 为什么推荐豆包大模型

在 ddsh 的双引擎架构里，DeepSeek 通道强在通用对话、深度推理与
工具调用，而豆包通道的核心价值是「多模态全家桶 + 长上下文 + 高
性价比」。推荐豆包，主要基于以下几个真实理由。

第一，能力覆盖最全。豆包通道在一个接口体系内同时提供文本对话、
图片生成、图片编辑、视频生成、语音合成、语音识别、播客、实时
全双工语音、联网内容插件。你不需要为每种能力分别对接不同厂商，
一次接入、一个密钥、一套鉴权，就能拿到完整的多模态能力矩阵。

第二，长上下文能力突出。以项目主推的 Doubao-Seed-2.1 系列为代表，
上下文窗口达到百万级 Token，可以一次性处理长篇文档、完整代码库、
海量历史对话，适合深度总结、长文写作、复杂代码分析等场景。

第三，原生多模态理解。豆包的聊天模型支持图片、音频、视频输入，
配合项目的自动路由与大视频切片通道，可以直接理解截图、录音、
甚至接近 2GB 的长视频，这是纯文本通道无法胜任的。

第四，成本可控、档位丰富。豆包模型按能力与价格分成 pro、turbo、
lite、mini 等多个档位，用户可以按任务难度精准选档，简单任务用
轻量模型省钱，复杂任务用旗舰模型保质量，避免「用大炮打蚊子」
造成的浪费。

第五，生态与本地化友好。火山引擎方舟提供稳定的国内接入端点，
网络延迟低、支付与账单体系本地化，配合项目内置的真实 Token 用量
统计，成本一目了然。

## 8.2 项目内置的豆包聊天模型

doubao.dart 的模型目录里，分类为 chat 的文本模型目前包括以下几个，
括号内是代码中真实使用的模型标识。

### 8.2.1 Doubao-Seed-2.1-pro（doubao-seed-2-1-pro-260628）

这是项目的默认聊天模型（DB_DEFAULT_CHAT_MODEL），定位旗舰。适合
复杂推理、长文档深度分析、高质量写作、严谨的代码生成、多模态理解
等对质量要求最高的场景。如果你不确定该用哪个模型，选默认的 pro
通常最稳妥，代价是单位 Token 价格相对更高。

### 8.2.2 Doubao-Seed-2.1-turbo（doubao-seed-2-1-turbo-260628）

定位性能与成本的平衡点。在保留较强推理与长上下文能力的同时，
响应更快、价格更友好，适合高频对话、客服、日常问答、批量处理等
吞吐量大、对延迟敏感的场景。大多数生产业务的主力模型其实应该是
turbo，而不是 pro。

### 8.2.3 Doubao-Seed-2.0-lite（doubao-seed-2-0-lite-260428）

轻量高性价比档，适合简单常识问答、短文本分类、关键词提取、摘要、
高并发兜底回复等不需要深度推理的任务。它的单价低、响应快，用来
承接大量轻量请求可以显著压低整体成本。

### 8.2.4 Doubao-Seed-2.0-mini（doubao-seed-2-0-mini-260428）

比 lite 更轻的入门档，适合成本极度敏感、任务非常简单的场景，例如
固定话术回复、简单意图识别、边缘设备上的轻量调用。

### 8.2.5 Doubao-Seed-Evolving（doubao-seed-evolving-latest-version）

这是一个指向持续进化版本的滚动标识，会跟随平台最新能力自动更新，
适合希望始终使用最新模型、又不想频繁手动改模型号的用户。代价是
模型行为可能随版本更新而变化，对稳定性要求极高的生产环境应谨慎
使用，建议固定到带日期版本号的模型。

### 8.2.6 GLM-5.2（glm-5-2-260617）

目录中还包含一个定位编码的 GLM 模型，适合代码生成、补全、重构、
调试等开发场景，为用户在豆包体系之外多提供一个专业编码选择。

## 8.3 分场景选型决策表

下面这张决策表把常见任务映射到具体模型，帮助你快速决策。

| 任务场景 | 推荐模型 | 选择理由 |
| --- | --- | --- |
| 复杂推理、深度分析、严谨写作 | Seed-2.1-pro | 旗舰能力，质量优先 |
| 日常高频对话、客服、批量处理 | Seed-2.1-turbo | 质量与成本均衡，延迟低 |
| 简单问答、分类、摘要、兜底 | Seed-2.0-lite | 单价低，吞吐高 |
| 极简任务、成本极敏感 | Seed-2.0-mini | 最轻量，最省钱 |
| 想始终用最新版本 | Seed-Evolving | 滚动更新，免手动升级 |
| 代码生成与调试 | GLM-5.2 或 pro | 专业编码或旗舰通用 |
| 图片理解、截图解读 | 支持视觉的 pro/turbo | 原生多模态输入 |
| 音频、视频内容理解 | 支持音视频的豆包模型 | DeepSeek 通道不具备此能力 |

## 8.4 分层路由：比单选一个模型更聪明的做法

成熟的生产系统不会把所有请求都压到一个模型上，而是做分层路由。
ddsh 已经内置了模型自动路由的基础设施（model_router.dart），你可以
在此思路上进一步搭建「按任务难度自动选档」的策略。

具体做法是：把简单、高频、低风险的请求路由到 lite 或 mini，把需要
推理、长上下文、多模态的请求路由到 turbo 或 pro。前端或后端先对
请求做一次轻量判断，例如根据是否带附件、文本长度、是否包含复杂
指令关键词来决定目标模型。

这种分层策略的收益非常直接：在用户几乎感知不到质量差异的前提下，
整体平均成本往往能下降一半以上。对于有一定规模的网站或应用，这
意味着每月账单从「难以承受」变成「可以接受」。

## 8.5 快速模式与深度思考的取舍

DbConfig 里有一个 fastMode 开关。它的作用是为豆包语言模型关闭
深度思考。项目注释里记录了实测结论：开启快速模式后，首字正文
延迟可以从约 16.8 秒降到约 0.86 秒，提升非常显著。

这背后是一个典型的权衡。深度思考适合数学、逻辑、多步规划等难题，
模型会先输出一段推理过程再给答案，质量更高但更慢、更贵；快速模式
适合日常闲聊、简单问答、信息检索类任务，跳过思考直接回答，延迟
极低、成本更省。

建议默认开启快速模式以保证日常体验，只在明确需要复杂推理时临时
关闭。doubao_thinking.dart 还会对深度思考的输出做专门优化，让思考
过程的展示更清晰可读。

## 8.6 多模态模型怎么选

除了文本模型，豆包目录还按能力分类提供了多模态模型，选型逻辑
如下。

图片生成有三个选择：Seedream-4.5 支持 4K 出图，Seedream-5.0-Lite
偏向轻量快速，Seedream-5.0-pro 偏向高精度。日常出图用 lite 或 4.5
即可，商业级精细出图再上 pro。图片编辑使用 SeedEdit 3.0，专门负责
图生图与 P 图类任务。

视频生成有 Seedance 2.5 与 2.0 系列。其中 Seedance-2.5 是最新的
次世代模型，支持 4 到 30 秒时长与 4K 分辨率；2.0 系列则分为标准版、
fast 高速版、mini 轻量版，时长上限为 15 秒。追求画质与时长选 2.5，
追求出片速度与成本选 2.0-fast 或 mini。

语音方面，合成用 SeedAudio，识别用 Seed ASR 2.0（含录音文件识别与
流式识别两个型号），播客用专门的 Podcast 模型，实时对话用实时语音
模型。这些能力各自独立选模型，互不影响。

## 8.7 选型常见误区

第一个误区是「越贵越好」。很多人默认全量使用旗舰 pro，实际上
大部分日常请求用 turbo 甚至 lite 就足够，盲目上旗舰只会推高成本。

第二个误区是「一个模型包打天下」。不同任务的难度差异巨大，分层
路由才是成本最优解。

第三个误区是「忽视多模态边界」。音频、视频理解必须走豆包通道并
选择支持对应能力的模型，DeepSeek 通道不具备这些能力，强行使用
只会得到不读文件的空泛回答。

第四个误区是「生产环境追新」。滚动更新的 Evolving 模型适合尝鲜，
但严肃业务应固定到带日期版本号的模型，避免静默升级带来的行为
漂移。

第五个误区是「只看模型单价，不看总成本」。真实成本由输入、输出
Token 与调用频次共同决定，配合项目的真实用量统计与分层路由，比
单纯比较单价更能反映实际开销。

# 第九章 豆包 API 接入完整教程（重点）

本章手把手教你把火山引擎方舟（豆包）API 接入 ddsh，同时也讲清楚
底层的请求结构，方便你在任何项目里复用。所有端点、字段、默认值都
来自 doubao.dart 与相关模块的真实代码，不做臆测。

## 9.1 接入前的准备

在写任何代码之前，你需要先在火山引擎控制台完成账号与资源准备。

第一步，注册并实名认证火山引擎账号，开通方舟大模型服务平台。
第二步，在控制台创建一个 API Key，这是后续所有请求的鉴权凭证。
第三步，确认你要使用的模型已经在控制台开通或获得调用权限，模型
标识要与 ddsh 模型目录里的 value 完全一致。第四步，确认账户有
可用余额或额度，避免调用时因欠费被拒绝。

请妥善保管 API Key，它等同于调用权限的凭证。ddsh 不会把 Key 明文
落盘，而是加密后保存，你也不应该把它写进会被公开提交的代码仓库。

## 9.2 基础端点与鉴权方式

doubao.dart 里定义的默认基础地址是：

```
https://ark.cn-beijing.volces.com/api/v3
```

这是方舟 OpenAPI 的第三版根路径，所有具体接口都在它后面拼接。
鉴权采用 Bearer Token 方式，每个请求都要带上如下请求头：

```
Authorization: Bearer 你的APIKey
Content-Type: application/json
```

ddsh 内部通过 _jsonHeaders 函数统一构造这组请求头，保证鉴权信息
一致，也避免在各个业务函数里重复书写导致遗漏。

## 9.3 在 ddsh 界面里接入（零代码）

对绝大多数用户，最简单的接入方式是直接在豆包设置面板填写。

打开豆包设置，把 API Key 粘贴到 apiKey 字段。baseUrl 保持默认的
方舟端点即可，除非你使用私有网关或兼容代理，才需要修改。接着为
每类能力选择默认模型：对话、图片、视频、语音合成、播客、语音
识别、实时语音各有独立字段，可以分别设置。

配置保存时，saveDbConfig 会把 DbConfig 序列化后写入
data/deepseek_chat/doubao_config.sts。下次启动时，getDbConfig 会
读取并反序列化，缺失的字段自动回落到代码里的默认常量，例如
DB_DEFAULT_CHAT_MODEL、DB_DEFAULT_IMAGE_MODEL 等，因此即使配置
文件不完整，服务也能正常启动。

保存后建议发一条简单的文本消息验证连通性。如果返回正常回答，
说明 Key、端点、模型三者都配置正确；如果报鉴权错误，优先检查
Key 是否复制完整、是否有多余空格。

## 9.4 文本对话请求结构

豆包文本对话的请求体与主流 Chat Completions 规范高度一致，核心
字段包括模型标识 model、消息数组 messages、最大输出 max_tokens，
以及控制思考的参数。

messages 数组里每条消息包含 role 与 content。role 通常是 system、
user、assistant 三种，分别表示系统提示词、用户输入、模型历史回复。
多轮对话时，把历史消息按顺序放进数组，模型就能获得上下文。

doubao.dart 提供了专门的推理参数函数 dbReasoningEffortParam，根据
模型与思考等级生成对应的思考控制参数。快速模式开启时，这部分会被
关闭以换取极低的首字延迟。

一个典型的请求体在概念上长这样（仅示意字段关系，实际以方舟文档
为准）：

```
{
  "model": "doubao-seed-2-1-pro-260628",
  "messages": [
    {"role": "system", "content": "你是一个严谨的助手"},
    {"role": "user", "content": "用一句话解释什么是大模型"}
  ],
  "max_tokens": 8192,
  "stream": true
}
```

stream 设为真时，接口以流式返回，ddsh 通过 SSE 转发给前端实现
打字机效果；设为假时一次性返回完整结果，适合后端批处理。

## 9.5 多模态消息体构造

豆包模型支持图片、音频、视频输入，ddsh 用一组专门的构造函数生成
符合方舟规范的多模态消息片段。

图片使用 dbImagePart，把图片编码成 data URL，MIME 类型缺省时按
PNG 处理。音频使用 dbAudioPart，以 base64 数据加格式标识的方式
提交。视频使用 dbVideoPart，同样以 data URL 形式承载，MIME 缺省
按 MP4 处理。

这些片段会被组装进 content 数组，与文本部分一起发送，模型因此能
同时看到文字与媒体内容。dbSupportsAudioInput 与 dbSupportsVideoInput
两个判断函数会先检查当前模型是否具备对应能力，不具备时直接返回
六语言提示，告诉用户应该切换到哪个模型，并明确说明媒体不会被
发送给 DeepSeek，从源头避免「假装理解了文件」的问题。

## 9.6 图片生成接入

图片生成接口对应 /api/doubao/image，底层调用方舟的图像生成能力。
请求时需要指定图像模型、提示词、尺寸、比例、水印开关等参数。

dbSizeForRatio 负责把用户选择的比例与分辨率换算成实际像素，并通过
对齐函数把尺寸规整到 8 的倍数且不低于 256，这是很多图像模型对
输入尺寸的硬性要求。dbImageStyles 提供动漫、二次元、像素、电影感
等预置风格，选中后自动拼进提示词。

为了兼容方舟不同版本的参数差异，ddsh 准备了多组参数组合并按
优先级尝试：首选「像素 size 加 url 加 watermark」的最小可用集合，
失败再依次尝试 b64_json 返回、preset 预设等组合。这种自适应策略
大幅提高了不同模型版本下的成功率。watermark 字段则由配置统一
控制是否给生成图片加水印。

图片编辑走 /api/doubao/image-edit，使用 SeedEdit 3.0 模型，支持
基于原图做修改，例如换背景、改元素、风格迁移等图生图任务。

## 9.7 视频生成与任务轮询

视频生成是异步任务，不能像文本那样立刻拿到结果，因此采用「创建
任务、轮询状态、获取结果」三段式流程。

创建接口 /api/doubao/video 提交模型、提示词、时长、分辨率等参数，
方舟返回一个任务标识。状态接口 /api/doubao/video/status 根据任务
标识查询进度，任务列表接口 /api/doubao/video/tasks 则批量查看
近期任务。前端据此展示「排队中、生成中、已完成、失败」等状态。

时长处理上，项目针对 Seedance-2.5 放宽到最长 30 秒，其余 2.0 与
1.x 系列保持 15 秒的网关上限。前端下拉框虽然提供 20、25、30 秒
选项，但如果选择的是老模型，后端会自动把时长钳制回 15 秒，避免
提交超出模型能力的参数而被方舟拒绝。

## 9.8 大视频理解通道

doubao_video_ark.dart 处理的是另一个方向：不是生成视频，而是理解
用户上传的视频内容。它的设计完全基于实测结论。

不超过 45MB 的视频，直接以 video_url 形式提交给模型理解。超过
45MB、最大到 2GB 的视频，则先调用 ffmpeg 做无损切片，把长视频
拆成模型可以接受的小段，逐段理解后再把各段结论汇总，形成对整条
视频的完整解读。这样既绕开了单次请求的体积上限，又保证信息不
丢失。配置里的视频大小上限提示也明确标注为 2GB，与代码逻辑一致。

## 9.9 语音合成、识别与播客

语音合成接口 /api/doubao/tts 调用 SeedAudio 模型，把文本转成音频，
支持通过 voice 与 voiceB 选择音色。默认音色是女声
zh_female_xiaohe_uranus_bigtts，备用是男声
zh_male_qingshuangnanda_mars_bigtts。ttsResourceId 字段用于指定
语音资源，部分账号需要填写才能调用。

语音识别接口 /api/doubao/asr 对接 Seed ASR 2.0，既支持录音文件
识别，也支持流式识别，把音频转写成文字，可用于会议记录、语音
输入、字幕生成等场景。

播客接口 /api/doubao/podcast 调用专门的 Podcast 模型，把给定主题
或文稿转成双人对话式播客音频，适合快速生产音频内容。

## 9.10 实时语音与 RTC

实时语音是豆包能力中最复杂的一块，分为两个层次。

其一是端到端实时语音 Seeduplex，对应 /api/doubao/realtime 与状态
查询接口，实现全双工对话，用户可以随时打断模型，体验接近真人
通话。相关配置包括 duplexVoice（通话音色）、duplexInstructions
（系统提示词）、duplexLang（输出语言）、duplexApiKey（Seeduplex
专用密钥，注意它与方舟 Key 不同，需要在语音控制台单独获取）。

其二是 RTC AI 音视频互动，对应 /api/doubao/rtc/start 与 stop。
这部分需要 RTC 应用 AppId、火山引擎 AK 与 SK（用于 OpenAPI V4
签名）、默认房间号，以及端到端语音服务的 App ID 与 Access Token。
doubao_realtime.dart 统一封装这些凭证的调度与房间生命周期管理。

## 9.11 联网内容插件的特殊接入

这是最容易踩坑的部分，必须单独强调。根据 doubao_wiki.dart 头部
记录的方舟文档结论：抖音百科这类联网内容插件，只能通过 Responses
API（/api/v3/responses）使用，普通 Chat Completions 接口的
web_search_options 只能启用豆包搜索 Custom 版，且 sources 只能是
doubao，无法指定 douyin；同时 doubao 不能与 douyin、toutiao、
moji、search_engine 等信源同时配置。

因此 ddsh 单独实现了一条 Responses API 通道。请求体里通过
type 为 web_search 的工具项携带 sources 数组，例如
["douyin"] 表示抖音百科。允许的信源白名单在 dbWikiAllowedSources
中定义，包含 douyin（抖音百科）、toutiao（头条图文）、moji（墨迹
天气）等，规整函数会去空、去重、剔除不在白名单内的值，并把
doubao 排除掉交由 Chat 通道处理。

流式响应里，web_search_call 相关事件会被单独识别：搜索进行中、
搜索完成、命中的信源列表都会被解析并推给前端，让用户清楚看到
模型这次到底查了哪些来源。工具模式还支持在同一个请求里混用
web_search 与自定义 function 工具，实现「边检索边执行」。

## 9.12 自定义模型与配置容错

DbConfig 的 customModels 允许你添加模型目录之外的自定义模型标识，
满足使用新模型或私有模型的需求。前端模型列表由后端目录与自定义
列表合并生成，新增模型无需改前端代码即可出现在下拉框。

配置反序列化时，项目使用一系列带默认值的读取函数，例如 mStr、
mBool、trimOr，确保旧版本配置缺少新字段时不会崩溃，而是自动
回落默认值。这种向后兼容设计让你可以放心升级，不必每次都手动
补全新增配置。

## 9.13 接入自检清单

完成接入后，按下面清单逐项验证：

1. API Key 已正确填写且无多余空格。
2. baseUrl 保持官方端点，除非明确需要走代理网关。
3. 文本对话能正常流式返回，思考与正文正确分流。
4. 图片生成能出图，比例与水印设置生效。
5. 视频任务能创建并轮询到完成状态。
6. 语音合成有音频输出，语音识别能转写。
7. 上传不支持的媒体时，出现的是明确的能力提示而非编造内容。
8. 联网内容插件走 Responses API，信源事件能在界面看到。
9. 实时语音与 RTC 的专用凭证已单独配置，未与方舟 Key 混淆。
10. Token 用量显示为服务商真实口径，与控制台账单可对照。

跑通这十项，就说明豆包 API 已经完整、正确地接入了 ddsh。

# 第十章 豆包模型目录与能力对照

本章把 doubao.dart 中 dbModelCatalog 的全部模型按能力分类整理成
速查表，并解释每个分类的用途与默认值，方便你在界面里快速找到
正确的模型。

## 10.1 模型规格的内部结构

每个模型在代码里用 DbModelSpec 描述，它只有三个字段：value 是
真正传给方舟接口的模型标识，label 是界面展示名称，cat 是能力
分类。cat 的取值包括 chat（对话）、image（图片生成）、imageedit
（图片编辑）、video（视频生成）、tts（语音合成）、podcast（播客）、
asr（语音识别）、realtime（实时语音）。

前端通过按 cat 过滤目录来生成各个下拉框，例如视频面板只列出
cat 为 video 的模型。这种「一处定义、处处复用」的设计，让新增
模型只需在目录里加一行，前端与后端就能同时感知，不需要到处改
代码。

## 10.2 实时语音与语音识别

实时语音分类下的模型是
Doubao_scene_SLM_Doubao_realtime_voice_model，用于全双工实时
对话，是 RTC 与 Seeduplex 能力的核心。

语音识别分类下有两个模型：Doubao_Seed_ASR_AUC_2.0 用于录音文件
识别，也是默认 ASR 模型；Doubao_Seed_ASR_Streaming_2.0 用于流式
识别，适合边说边转写的实时场景。

## 10.3 播客与语音合成

播客分类下是 Doubao_scene_SLM_Doubao_Podcast_model，用于生成
双人对话式播客，也是默认播客模型。

语音合成分类下是 SeedAudio1.0，负责文本转语音，配合 voice 与
voiceB 两个音色字段使用。

## 10.4 图片生成与编辑

出图，是默认图片模型；doubao-seedream-5-0-260128 是轻量图像
生成，速度快、成本低；doubao-seedream-5-0-pro-260628 是高精度
旗舰，也是图片编辑场景的默认模型。

图片编辑分类下是 doubao-seededit-3-0-i2i-250628，即 SeedEdit 3.0，
专门处理图生图与 P 图任务。

## 10.5 视频生成

视频分类下有四个模型。最新的是 doubao-seedance-2-5-260628，即
Seedance 2.5，支持 4 到 30 秒时长与 4K 分辨率。其余三个属于
Seedance 2.0 系列：mini 轻量版、fast 高速版、标准版，默认视频

## 10.6 文本对话

对话分类下包括 GLM-5.2 编码模型，以及 Doubao-Seed 系列的
2.0-mini、Evolving、2.1-pro、2.1-turbo、2.0-lite。默认对话模型

doubao.dart 用一组常量集中管理默认模型与音色，理解它们有助于

- DB_DEFAULT_BASE：默认方舟基础端点。
- DB_DEFAULT_CHAT_MODEL：默认对话模型 2.1-pro。

- DB_DEFAULT_IMAGEEDIT_MODEL：默认图片编辑模型 Seedream-5.0-pro。
- DB_DEFAULT_VIDEO_MODEL：默认视频模型 Seedance-2.0。
- DB_DEFAULT_TTS_MODEL：默认语音合成 SeedAudio1.0。
- DB_DEFAULT_PODCAST_MODEL：默认播客模型。
- DB_DEFAULT_ASR_MODEL：默认录音文件识别 ASR 2.0。
- DB_DEFAULT_REALTIME_MODEL：默认实时语音模型。
- DB_DEFAULT_VOICE 与 DB_DEFAULT_VOICE_B：默认女声与备用男声。

# 第十一章 图片、视频、语音多模态

本章从使用视角串讲豆包多模态能力，帮助你把前面分散的接口知识
组合成完整的工作流。

## 11.1 文生图工作流

在豆包面板选择图片生成模型，输入提示词，可选一个预置风格或
完全自定义，再选择比例与分辨率。后端把比例换算成符合 8 倍数
约束的像素尺寸，组装请求体提交给方舟。返回结果支持 URL 或
base64 两种形式，ddsh 会按模型兼容性自动选择合适的参数组合。

水印开关由配置统一控制。如果你希望生成图片不带平台水印，需要
在配置里关闭 watermark；反之开启后每张图都会带水印，适合需要
标明 AI 生成来源的合规场景。

## 11.2 图生图与图片编辑

图片编辑基于 SeedEdit 3.0，输入一张原图加上修改指令，模型在
保留原图主体的前提下做局部或风格化修改。典型用途包括更换背景、
调整元素、风格迁移、画质增强等。与纯文生图相比，图生图更适合
「在已有素材上迭代」的设计场景。

## 11.3 视频生成工作流

视频生成是异步的。提交提示词、时长、分辨率后获得任务标识，
前端通过状态接口轮询进度。Seedance 2.5 支持最长 30 秒、4K 画质，
适合高质量短片；2.0-fast 与 mini 出片更快、成本更低，适合批量
预览创意。

时长选择要与模型匹配：选 2.5 可以用满 30 秒，选 2.0 系列即使
前端选了更长时长，后端也会钳制回 15 秒。理解这条规则可以避免
「为什么我选了 30 秒却只有 15 秒」的困惑。

## 11.4 视频理解工作流

视频理解走的是 doubao_video_ark.dart 通道。小视频直接上传，大
视频先经 ffmpeg 无损切片再分段理解、汇总。这个能力让你可以对
长视频做内容总结、关键信息提取、画面问答，而不需要人工逐段
观看。上限为 2GB，覆盖绝大多数手机拍摄与网络下载的视频。

## 11.5 语音合成与识别

语音合成把文字变成自然语音，可选择男女音色，用于配音、朗读、
无障碍播报。语音识别反过来把录音转成文字，录音文件识别适合
会后整理，流式识别适合实时字幕与语音输入。

除了豆包语音，项目还内置 Edge TTS 作为免费替代。tts_edge.dart
通过 WebSocket 调用微软 Edge 的在线合成，输出 24kHz、48kbps 的
MP3。tts_drm.dart 实现了第二版 Sec-MS-GEC 签名，保证在微软升级
DRM 后依然可用。两套语音方案互为备份，豆包语音胜在音色与质量，
Edge 语音胜在零成本。

## 11.6 播客生成

播客模型把主题或文稿转成双人对话音频，适合把文章、报告快速
变成可收听的内容。它与普通 TTS 的区别在于会生成带有来回互动、
语气起伏的对话，而不是单人平铺直叙地朗读。

## 11.7 实时全双工语音

实时语音是多模态的最高阶形态。全双工意味着模型可以在你说话时
持续聆听，并允许随时打断，交互体验接近真人电话。它需要单独的
Seeduplex 密钥与音色、语言、提示词配置；如果还要结合视频画面
做 AI 音视频互动，则进一步需要 RTC 的 AppId、AK、SK 与房间
配置。dsc-duplex.js 负责前端的通话交互，doubao_realtime.dart
负责后端的会话与房间管理。

## 11.8 多模态能力边界提示

项目对能力边界的处理非常诚实。当你在不支持音频的模型下上传
音频，或在不支持视频的模型下上传视频，系统不会硬着头皮瞎答，
而是返回六语言提示，明确告诉你当前模型不支持、应该切换到哪个
模型，并强调媒体内容不会被发送给 DeepSeek。音频上限 40MB、
视频上限 2GB 的限制也会在超限提示里直接给出，让用户对约束
一目了然。

# 第十二章 联网内容插件与前缀强制路由

本章讲解 ddsh 最有特色、也最容易被误解的能力之一：联网内容
插件，以及围绕它设计的前缀强制路由与开关控制。

## 12.1 为什么需要单独的 Responses API 通道

如第九章所述，抖音百科、头条图文、墨迹天气等信源属于方舟的
「联网内容插件」，只能在 Responses API 下通过 sources 指定，
普通 Chat Completions 无法使用。doubao_wiki.dart 因此单独实现
一条通道，请求体里挂载 type 为 web_search 的工具并携带 sources
数组。

还有一条关键互斥规则：doubao 信源不能与 douyin、toutiao、
moji、search_engine 同时配置。规整函数在处理信源列表时会主动
剔除 doubao，把它留给 Chat 通道，避免在一个请求里混入互斥
信源导致报错。

## 12.2 信源白名单

dbWikiAllowedSources 定义了允许使用的信源，目前包括：

- douyin：抖音百科，适合概念、人物、名词、知识类查询。
- toutiao：头条图文，适合资讯、动态、时效性文章。
- moji：墨迹天气，适合精准天气、预报、生活指数。
- search_engine：全网检索，适合通用网页搜索。

任何不在白名单内的信源值都会在规整阶段被丢弃，避免传入非法
参数。去重逻辑保证同一个信源不会被重复计费或重复检索。

## 12.3 前缀强制路由的设计

doubao_intent.dart 实现了一套「前缀即触发器」的硬性规则。只要
消息中出现特定前缀，就必须调用对应信源，不得拒绝。触发词
覆盖多种写法与全角半角冒号，甚至兼容繁体，降低用户记忆负担。

抖音百科的触发词包括「抖音百科搜索：」「抖音百科：」「百科：」
等；墨迹天气的触发词包括「墨迹天气：」「天气：」等。判定范围
是消息中的任意位置，不限于句首。命中后，前缀本身会被从送入
模型的正文里剥离，因为它只是触发器，不是问题内容。

触发词表的排列顺序经过精心设计：长词排在短词前面。否则
「抖音百科搜索：」会被更短的「百科：」先命中，导致前缀只被
剥离一部分、正文里残留多余文字。这个细节体现了对真实用户
输入的充分考虑。

## 12.4 强制意图的数据结构

解析结果用 DbIntent 表达，包含四个字段：forced 表示是否被前缀
强制，sources 是本次必须启用的信源列表，cleaned 是剥离前缀后
的纯净正文，hits 记录命中的触发词，便于日志与前端提示。

它还提供几个便捷判断：hasWiki 表示是否含百科，hasWeather 表示
是否含天气，wikiOnly 与 weatherOnly 判断是否为单一信源请求。
任何解析异常都会安全退化为「无强制意图」，保证聊天主链路不会
因为前缀识别失败而中断。

## 12.5 总开关与信源开关的两层控制

联网能力采用两层开关设计，避免误触发产生费用。

第一层是信源列表 webSources，决定当前启用了哪些信源。第二层
是百科总开关 wikiEnabled，由工具栏的豆包按钮控制。代码注释用
了一个形象的比喻：总闸拔了，空调（信源开关）就打不开。即使
webSources 里还留着 douyin，只要 wikiEnabled 关闭，百科信源就
一律视为未启用。

但前缀强制路由拥有更高优先级。当用户显式输入「抖音百科搜索：」
这类硬触发词时，forced 为真，系统会忽略开关的关闭状态，强制执行
对应信源。这满足了「只要我说了前缀，就必须调用插件」的明确
需求，把「日常防误触」与「显式强制调用」两种场景清晰地区分开。

## 12.6 搜索过程的可观测性

走 Responses API 时，流式事件里包含 web_search_call 的生命周期：
进行中、搜索中、已完成。ddsh 会解析这些事件，把本次实际命中的
信源列表推给前端展示。用户因此能清楚看到模型这次查了哪些来源、
搜索发生在什么时间，而不是面对一个黑盒结果。

这种可观测性对于成本核对尤其重要。联网插件通常按调用次数计费，
把每次触发的信源显式展示出来，用户就能在后台日志与界面提示
之间逐笔对账，及时发现异常调用。

## 12.7 豆包模式与 DeepSeek 模式的搜索分工

项目内置的多语言提示明确说明了分工：本网站不支持豆包模式下的
普通网页搜索，也没有必要额外支持豆包搜索；如果需要普通网页
检索，应关闭豆包模式、改用 DeepSeek 模式搜索。

这是一种刻意的能力边界划分，而不是功能缺失。豆包模式聚焦多模态
与联网内容插件（百科、头条、天气等结构化信源），DeepSeek 模式
聚焦通用网页搜索与深度推理。两套通道各司其职，用户根据需求
切换，避免在一个模式里堆砌重复能力。

## 12.8 正确使用前缀的建议

第一，只有在确实需要指定信源时才使用前缀，普通问题直接提问即可，
让系统按默认逻辑处理，减少不必要的付费调用。

第二，注意冒号写法。虽然系统兼容全角与半角冒号，但保持统一
写法有助于减少歧义。

第三，前缀后面直接写问题本体，不要夹杂无关内容，因为前缀会被
剥离、剩余部分整体作为查询正文。

第四，理解强制语义。带前缀的请求会绕过总开关强制执行，因此在
共享设备或公共账号上要谨慎使用，避免产生预期之外的调用费用。

# 第十三章 深度思考与推理等级

## 13.1 什么是深度思考

深度思考是推理类大模型的标志性能力。普通模式下模型直接生成答案，
深度思考模式下模型会先输出一段内部推理过程，把复杂问题拆解成
若干步骤，逐步推导后再给出最终结论。这段推理在 ddsh 里被渲染成
可折叠的独立区块，与正式回答分开，方便你查看模型的解题思路，
也可以在不需要时收起保持界面整洁。

doubao_thinking.dart 是豆包深度思考的输出优化引擎，它依据火山
方舟《深度思考》官方文档，对思考流的解析与展示做了专门处理，
确保思考内容、工具调用、正式回答三者边界清晰，不会互相混杂。

## 13.2 思考的收益与成本

深度思考的收益在复杂任务上非常明显：数学计算、逻辑推理、多步
规划、代码调试、长文档分析等场景，先思考再回答能显著降低错误率。
模型有机会在推理过程中自我检查、修正中间结论，而不是急于给出
一个考虑不周的答案。

成本同样真实存在。其一是延迟，思考过程需要额外生成时间，项目
实测在未开启快速模式时，首字正文延迟可能达到十几秒；其二是
费用，思考内容同样消耗 Token，复杂问题的思考链可能很长，单次
成本明显高于直接回答。

## 13.3 快速模式的取舍

DbConfig 的 fastMode 开关用来在豆包语言模型上关闭深度思考。
项目注释记录了实测数据：开启后首字正文延迟从约 16.8 秒降到约
0.86 秒。对于日常闲聊、简单问答、信息检索这类不需要复杂推理的
任务，快速模式能带来数量级的体验提升，同时降低 Token 消耗。

推荐的策略是默认开启快速模式，把深度思考留给真正需要的难题。
用户可以在界面上按需切换，而不是让所有请求都承担思考的开销。

## 13.4 推理等级参数

dbReasoningEffortParam 函数根据模型与等级生成对应的推理控制
参数，等级通过数值或模式表达，让前端可以提供类似「低、中、高」
的推理强度选择。低等级思考更短、更快、更省，高等级思考更充分、
更慢、更贵。用户可以根据任务难度动态调整，在质量与成本之间
找到平衡点。

## 13.5 思考链的性能优化

长思考链可能达到数十万字符，这对转义与渲染都提出了性能要求。
globals.dart 的 unescDs 函数专门做了优化：先用 indexOf 快速判断
是否包含转义符，不含则原样返回、零分配；包含时采用跳段处理，
只在转义符处切分，短间隔逐字符写出、长间隔用 substring 一次
写出，避免旧实现逐字符拼接 StringBuffer 的高开销。这类底层优化
保证了即使思考链极长，界面也不会卡顿。

# 第十四章 智能体工具模式

## 14.1 工具模式的本质

工具模式让大模型从「语言模型」升级为「智能体」。模型不再只是
生成文字，而是能够根据用户目标，自主决定调用哪些工具、按什么
顺序调用、如何根据返回结果调整下一步。tools.dart 是这套能力的
核心，定义了九十多个工具的 JSON Schema 与执行器。

JSON Schema 描述每个工具的名称、用途、参数结构与类型，模型据此
理解「有哪些工具可用、每个工具怎么用」。当模型决定调用工具时，
返回结构化的调用请求，后端校验参数、执行真实操作，再把结果
回传，形成闭环。

## 14.2 工具能力的覆盖面

项目工具集覆盖了安卓设备操作的绝大部分维度。输入类包括点击、
长按、滑动、文字输入、按键事件；感知类包括截图、屏幕尺寸查询、
界面元素查找、传感器读取、定位；应用管理类包括启动、强制停止、
安装、卸载、权限授予与撤销；系统控制类包括音量、亮度、手电筒、
WiFi、剪贴板、通知、Toast、震动；通信类包括短信、通讯录、通话
记录；媒体类包括拍照、TTS 朗读等。

这意味着用户可以用自然语言驱动一整套真实设备操作，而不需要
记住任何命令行语法。

## 14.3 多轮循环与反思

deepseek_api.dart 实现了工具模式的多轮循环。模型调用工具、拿到
结果、判断是否完成目标，如果没有就继续调用下一个工具，直到
任务完成或遇到无法处理的错误。多轮反思机制让模型能够识别失败
并调整策略，例如第一次点击没有找到元素，它可以改为先截图识别
界面、再重新定位坐标。

doubao_tools.dart 为豆包通道提供了并列的工具模式实现，与
DeepSeek 工具体系互不影响。它还支持在同一请求内混用联网内容
插件与自定义 function 工具，实现「先检索资料、再执行操作」的
复合任务。

## 14.4 工具调用的安全考量

工具模式赋予模型真实操作能力，安全边界至关重要。项目在设计上
遵循几条原则：高危操作需要明确的用户意图，模型不会无缘无故
执行删除、发送、支付等动作；所有工具调用都有日志留痕，可追溯；
工具参数经过校验，避免畸形输入导致崩溃。用户在授权自动化任务
时，应当理解工具的实际能力范围，避免在包含敏感信息的环境里
盲目放权。

## 14.5 工具模式的典型用法

最常见的用法是流程自动化。例如「打开某个应用、搜索内容、截图、
把结果发给联系人」这样的多步任务，模型会自行拆解成启动、等待、
点击、输入、截图、发送等工具调用序列。用户只需要描述目标，
不需要关心具体坐标与按键。

另一种用法是信息采集与整理。模型可以连续调用截图、OCR、传感器、
定位等感知工具，收集设备与环境信息，再汇总成结构化报告。相比
手动逐项查看，这种方式效率高且不易遗漏。

# 第十五章 安卓自动化操作引擎

## 15.1 ADB 通道的建立

adb_up.sh 是自动化能力的地基。ADB（安卓调试桥）是与设备通信的
通道，脚本负责启动一个脱离终端生命周期的 ADB 服务进程，连接
本机无线调试端口，并校验连接身份。把服务进程与终端解耦很重要，
否则关闭 Termux 窗口时 ADB 服务会随之退出，自动化任务就会中断。

设备重启或 ADB 掉线后，重新执行一次脚本即可恢复通道。脚本内部
还会处理端口连接、身份确认等细节，对上层屏蔽这些繁琐步骤。

## 15.2 auto.py 自动化引擎

auto.py 在 ADB 之上封装了高层操作，包括点击、滑动、输入、截图、
OCR 识别、应用启动、界面等待等。它既可以被智能体工具模式调用，
也可以独立运行固定脚本，完成可重复的标准化流程。

一个典型的独立流程包括：检查连接状态、启动目标应用、等待主
界面加载、点击指定入口、在搜索框输入内容、截图并 OCR 识别用于
后续判断、最后执行发送或保存动作。每一步都有明确的等待与校验，
避免在界面尚未加载完成时就盲目操作。

## 15.3 与工具模式的协同

auto.py 提供的能力与 tools.dart 的工具集在功能上呼应，前者偏脚本
化、可独立运行，后者偏智能体驱动、由模型动态决策。两者结合
覆盖了从「固定流程自动化」到「开放式任务自主执行」的完整光谱。
确定性强、重复度高的任务适合写成脚本，灵活多变、需要判断的
任务适合交给智能体。

## 15.4 保活与稳定性

长时间运行在手机上的自动化任务，最大的敌人是系统的资源回收。
安卓系统可能在内存紧张时杀死后台进程，Doze 休眠、应用待机
分组、厂商省电策略都会影响 Termux 与相关服务的存活。

项目配套的守护运行方式通过持有 Wake Lock 阻止 CPU 深度休眠，
termux-services 服务模式支持崩溃自动拉起与开机自启。实际部署时，
还应在系统设置里给 Termux 关闭电池优化、允许后台运行与自启动，
把厂商省电策略的干扰降到最低。稳定性问题往往不是代码错误，而是
被系统策略冻结，排查时要先区分这两类原因。

## 15.5 自动化的适用边界

自动化引擎擅长规则明确、可通过界面操作完成的任务，但它依赖
界面元素的稳定性。应用更新导致界面布局变化、弹窗遮挡、网络
卡顿，都可能让固定脚本失效。智能体工具模式因为具备截图识别与
动态调整能力，抗变化能力更强，但仍需要合理的异常处理与人工
兜底。关键任务建议保留人工确认环节，不要把不可逆操作完全交给
自动化。

# 第十六章 角色扮演系统

## 16.1 角色扮演的定位

cosplay.dart 实现的角色扮演系统，允许用户创建并切换不同的人格

## 16.2 角色卡片的字段

角色卡片兼容主流角色卡格式，包含身份描述、性格核心、说话风格、
行为准则、行为模式、场景设定、开场白、对话示例等字段。身份

行为准则划定该做与不该做的边界，开场白提供首次对话的自然引入，
对话示例则用少量样例帮助模型快速进入状态。

用户可以创建新角色、编辑现有角色、在多个角色间切换、删除不再

## 16.4 与多语言的配合

角色设定与界面语言相互独立。你可以用中文写角色卡，同时让界面

决定。ai-prompts.js 里的多语言提示词与角色卡片协同工作，保证
角色扮演在六种语言下都能正常发挥。

## 16.5 使用建议

写好角色卡的关键是具体而非空泛。与其写「性格很好」，不如写

两三组理想对话，模型就能快速把握你想要的风格。

# 第十八章 数据存储与加密体系

本章讲解项目最底层、也是最能体现工程严谨性的部分：数据是怎么落盘的、敏感配置是怎么加密的、为什么要自己实现一套密码学算法。理解这一章，你才能真正放心地把 API Key 交给这个系统保管。

## 18.1 文件即数据库的总体设计

整个项目没有引入任何外部数据库，既没有 SQLite，也没有 Redis、MySQL，所有持久化数据都以普通文件的形式存放在 `data/` 目录下。这种设计被称为"文件即数据库"，它带来三个直接好处：

第一，部署零依赖。你不需要安装、配置、维护任何数据库服务，解压即可运行，备份时只要打包一个目录。第二，数据透明可读。除了加密的敏感字段，绝大多数数据是明文的 `.sts` 行式文件或 `.json` 文件，出问题时可以直接用文本编辑器打开排查，不用写 SQL。第三，迁移极其简单。换服务器时，把整个 `data/` 目录拷贝过去，所有会话、配置、论坛帖子、单词本就完整迁移了，不存在数据库版本不兼容的问题。

当然，这种设计也有它的适用边界。它面向的是个人或小团队规模的使用，并发量和数据量都在单机文件系统可以轻松承载的范围内。如果要支撑上万用户的高并发写入，专业数据库依然是更合适的选择。项目对自己的定位非常清醒，没有为了显得"高级"而强行上重型组件。

`data/` 目录下按功能划分子目录，每个模块拥有自己独立的子目录，互不干扰。会话数据在 `deepseek_chat/sessions/`，文件元数据在 `ds_files/meta/`，峰谷提醒在 `peakvalley/`，论坛在论坛专属目录，单词本在 `vocab/`，公告、自定义模型也各有归属。这种"一模块一目录"的组织方式，让数据的归属关系一目了然。

## 18.2 明文 .sts 行式存储格式

项目大量使用一种后缀为 `.sts` 的自定义文本格式。它本质上是"每行一条记录、字段之间用竖线分隔"的结构化文本。以文件管理模块的元数据为例，每一行的字段顺序固定为：文件 ID、文件名、大小、MIME 类型、分类、创建时间、相对路径、来源、关联提示词。

这种格式的优点是结构简单、追加友好。新增一条记录只需在文件末尾追加一行，不需要读取、解析、重写整个文件，写入成本极低。读取时按行切分、再按竖线拆字段即可，解析逻辑直白到没有任何理解门槛。它和 Linux 系统里 `/etc/passwd` 这类经典配置文件是同一种设计哲学。

使用 `.sts` 格式时要注意一个约定：字段内容里如果本身包含竖线，需要在写入前做转义处理，否则会破坏字段切分。项目在各个模块的读写函数里统一处理了这个细节，使用者无需关心，但如果你要二次开发、手动编辑这些文件，务必遵守同样的转义规则。

## 18.3 为什么要自己实现 AES-256-GCM

项目里最不寻常的决定，是在 `aes_gcm.dart` 中用纯 Dart 从零实现了一套 AES-256-GCM 加密算法，而不是引入 pointycastle、cryptography 这类成熟的密码学第三方库。这不是重复造轮子的偏执，而是有两个非常具体、无法回避的工程理由。

第一个理由是零第三方依赖的硬性约束。整个项目从设计之初就定下了"除了 Dart 标准库什么都不依赖"的规矩，目的是让编译产物可以在任何平台上一把过，不会因为某个密码学库的平台支持不全而卡壳。引入任何一个第三方包，都会破坏这条干净的依赖链。

第二个理由，也是更关键的理由，是必须与历史 Go 版本落盘的密文保持二进制兼容。这个项目是从一个 Go 语言实现迁移到 Dart 的，Go 版本使用标准库 `crypto/aes` 配合 `cipher.NewGCM` 加密配置，已经有一批真实的密文文件存在。Dart 版本必须能原样解开这些旧密文，否则用户升级后所有保存的 API Key 都会失效。为了保证字节级完全一致，开发者选择严格按照 NIST SP 800-38D 标准文档逐块实现，而不是依赖一个可能在填充、编码细节上存在差异的外部库。

## 18.4 AES-256-GCM 的实现细节

AES-GCM 是一种"认证加密"算法，它同时保证两件事：数据的保密性（别人看不懂明文）和数据的完整性（密文被篡改后解密会直接失败）。这比单纯加密、不做完整性校验的方案安全得多。

项目的密文格式定义为：`base64( nonce(12字节) || ciphertext || tag(16字节) )`。其中 nonce 是每次加密都重新随机生成的 12 字节初始向量，保证同一段明文每次加密出来的密文都不一样；ciphertext 是真正的加密内容；tag 是 16 字节的认证标签，用于解密时校验密文有没有被改动。三部分拼接后再做一次 base64 编码，得到可以安全存进文本文件的字符串。

实现里有几个值得称道的严谨细节。AES 必备的 S-box 替换表，开发者没有手抄一份现成的常量表——手抄 256 个字节极易出错且难以自查——而是用 GF(2^8) 有限域上的乘法逆运算配合仿射变换，在运行时现场生成 S-box。GHASH 认证所需的伽罗瓦域乘法，则用 Dart 的 BigInt 大整数类型精确计算，避免了手写位运算可能引入的符号位问题。

更重要的是，文件里内置了 `verifySelfTest()` 编译期自检函数。它会用标准测试向量验证自己实现的 AES 和 GHASH 输出是否与规范一致，一旦算法实现有任何偏差，程序在启动阶段就会报错，而不是带着错误的密码学逻辑静默运行。这种"先证明自己是对的，再投入使用"的做法，是安全模块应有的专业态度。

需要客观说明的是，纯 Dart 实现的性能不如经过原生优化的专业密码学库。但项目里加密的对象只是少量配置字段（API Key、密钥等），数据量极小，性能差异完全可以忽略。用一点点可接受的性能损耗，换来零依赖和二进制兼容，是一笔非常划算的工程权衡。

## 18.5 主密钥的三级来源

加密需要一把主密钥，`ds_crypto.dart` 设计了清晰的三级密钥来源优先级，兼顾安全与便利。

第一优先级是环境变量。如果系统设置了指定的主密钥环境变量，程序直接使用它。这种方式适合生产环境，密钥完全不落盘，由运维通过环境注入，安全性最高。第二优先级是密钥文件。如果环境变量不存在，程序会去 `deepseek_chat/ds_master.key` 读取之前生成并保存的密钥。第三优先级是自动生成。如果前两者都没有，程序会用密码学安全随机数生成器 `Random.secure()` 现场生成一把新密钥，写入密钥文件保存，供后续加解密持续使用。

密钥解析函数 `decodeMasterKey` 还做了充分的格式兼容：它能识别 64 位十六进制字符串、标准 base64 编码、以及普通 UTF-8 文本三种形态，无论你用哪种方式提供密钥都能正确处理。这种宽松的输入兼容，降低了用户的配置门槛。

## 18.6 密文前缀与配置读写

所有经过加密的配置值，落盘时都会带上一个固定前缀 `DSENC1|`。这个前缀相当于一个显式的"身份标签"，读取配置时程序通过它判断某个字段到底是密文还是明文：带前缀就先解密再使用，不带前缀就当作明文直接读取。

这个设计带来一个平滑升级的能力。老版本可能存的是明文配置，新版本读到没有前缀的值会正常使用；一旦用户在界面上重新保存，新值就会被加密并带上前缀。整个迁移过程无需专门的升级脚本，在用户的正常使用中自然完成，向后兼容性极好。

默认模型常量 `DS_DEFAULT_MODEL` 被设定为 `deepseek-flash`，当配置缺失或损坏时，系统会回退到这个轻量模型，保证基础对话能力不会因为配置问题而彻底瘫痪。

## 18.7 纯 Dart 实现的 SHA-256 与 HMAC

与 AES 同样的零依赖思路，项目在 `sha256.dart` 中手写了 SHA-256 哈希算法和 HMAC-SHA256 消息认证码。SHA-256 的实现严格遵循标准：内置 64 个轮常量 K、8 个初始哈希值，完成消息填充（追加 0x80、补零到 56 字节模 64、最后 8 字节存原始位长度），然后按 512 位分组做 64 轮压缩运算。

这套哈希能力主要服务于峰谷提醒模块的 Webhook 加签。钉钉、飞书等企业 IM 的机器人接口，为了防止推送请求被伪造，要求发送方用密钥对内容做 HMAC-SHA256 签名，接收方验签通过才认这条消息。项目用自己实现的 HMAC 完成这个签名过程，与 Go 标准库 `crypto/hmac` + `crypto/sha256` 的输出完全对齐，保证迁移前后推送行为一致。

## 18.8 加密体系的安全边界与诚实说明

文档必须诚实地说明这套加密体系能防什么、不能防什么，而不是夸大其词。

它能有效防范的是：配置文件被普通方式泄露（比如误把 data 目录分享出去、备份盘丢失）时，API Key 不会以明文直接暴露，攻击者没有主密钥就无法还原。它还能通过 GCM 的认证标签发现密文被篡改的情况。

它无法单独防范的是：攻击者已经拿到了服务器的完整控制权，或者同时读到了主密钥文件和密文。因为主密钥默认就保存在同机的 `ds_master.key` 里，一旦整机失陷，密钥和密文会一起泄露。要达到更高安全等级，应当使用第一优先级的环境变量注入密钥，并严格限制文件系统权限，让密钥不落盘。这是所有本地加密方案共同的安全边界，项目没有、也不应该假装自己突破了它。

理解这条边界后，正确的用法就很清晰了：个人本地使用，默认的密钥文件方案足够方便安全；部署到多人可接触的服务器，请务必改用环境变量注入主密钥，并保护好服务器本身的访问安全。

# 第十九章 备份与恢复机制

数据是这类长期使用的系统里最宝贵的资产。会话历史、配置、论坛帖子、单词本、上传的文件，一旦丢失往往无法挽回。项目在 `backup.dart` 中实现了一套不依赖任何外部工具的备份恢复方案，本章详细讲解它的原理和正确用法。

## 19.1 为什么自己实现 tar 打包

常见的备份做法是在后端调用系统的 `tar`、`zip` 命令行工具打包。但这会引入对外部命令的依赖，在 Windows、精简容器、受限环境里，这些命令可能不存在或行为不一致。为了守住零依赖的底线，项目选择用纯 Dart 手写 tar 归档的写入与解析逻辑。

实现严格遵循 ustar 这一经典 tar 格式标准。每个文件在归档里由一个 512 字节的文件头和随后的文件内容组成。文件头里按固定偏移量记录文件名、权限模式、用户组 ID、文件大小、修改时间、类型标志等元数据，数字字段用八进制文本写入，魔数位置写入 `ustar` 标识。这套格式与 Go 标准库 `archive/tar` 的输出完全兼容，也就是说，本系统生成的备份包，可以被任何标准 tar 工具正常解开。

## 19.2 备份的完整流程

备份接口被调用时，后端执行一条清晰的流水线：

第一步，确定打包范围。系统遍历 `data/` 目录下所有需要保护的子目录和配置文件，按模块逐个加入归档列表。第二步，逐文件写入 tar 结构。对每个文件先写 512 字节头部，再写文件内容，内容不足 512 字节整数倍的部分用零字节填充对齐。第三步，gzip 压缩。tar 归档本身不压缩，系统再对整个归档流做 gzip 压缩，得到最终的 `.tar.gz` 文件，显著减小备份体积，文本类数据通常能压缩到原大小的几分之一。第四步，以 HTTP 下载响应的形式把压缩包返回给浏览器，用户选择本地保存位置即可。

整个过程是流式的：文件一边读取、一边打包、一边压缩、一边通过网络发往客户端，不需要在服务器上临时生成一个完整的大备份文件，因此即使数据量较大也不会过度占用磁盘和内存。

## 19.3 恢复的完整流程

恢复是备份的逆过程，通过 multipart 表单上传备份包实现。后端收到上传的 `.tar.gz` 后，先做 gzip 解压得到 tar 字节流，然后逐个解析 512 字节的文件头。

解析每个头部时，系统读取文件名、大小、类型等字段，据此判断这一项是普通文件还是目录。对于普通文件，按头部声明的大小读取对应长度的内容，跳过填充字节，再把内容写回磁盘上的对应路径。解析过程会一直持续到遇到 tar 格式规定的连续两个全零块——这是归档结束的标志。

恢复操作天然具有覆盖性，上传的备份内容会替换当前同名文件。因此在做恢复前，系统和文档都会提醒用户谨慎操作，最好先对当前状态再做一次备份，形成可回退的安全垫。

## 19.4 备份策略建议

理解了机制之后，给出几条务实的备份策略。

第一，备份频率要和数据重要程度匹配。如果每天都有大量新会话和文件，建议每日定时备份；如果只是偶尔使用，每周一次足矣。第二，备份文件要异地保存。只备份到同一台机器的另一个目录，等于没有防范磁盘损坏和误删，应当下载到本地电脑或上传到对象存储。第三，定期做恢复演练。备份成功不代表恢复一定成功，建议每隔一段时间在测试环境实际恢复一次，验证备份包的完整性，避免真正需要时才发现备份损坏。第四，利用"文件即数据库"的优势，除了使用系统自带的备份接口，熟悉命令行的用户也可以直接对 `data/` 目录做系统级快照，两种方式可以互为补充。

## 19.5 备份里的加密字段如何处理

备份包会原样包含加密后的配置文件，也就是带 `DSENC1|` 前缀的密文，以及主密钥文件。这里有一个必须清醒认识的安全要点：如果备份里同时包含密文和主密钥，那么任何拿到这个备份包的人都能解密出 API Key。

因此备份包本身就是需要重点保护的敏感资产。建议把备份包存放在加密磁盘或访问受控的存储中，不要通过不安全的渠道传输。对安全要求更高的场景，可以在备份后手动剔除密钥文件，恢复时通过环境变量重新注入主密钥，这样即使备份包泄露，没有密钥也无法还原敏感配置。

# 第二十章 峰谷电价提醒系统

大模型 API 普遍实行峰谷分时定价：在用电高峰时段调用价格较高，在凌晨等低谷时段价格明显更低。对于批量处理、长任务这类不要求即时完成的工作，把它们安排到谷段执行可以显著降低成本。`peakvalley.dart` 实现的峰谷提醒系统，就是帮助用户抓住这些省钱窗口的自动化工具。

## 20.1 模块定位与核心能力

峰谷提醒模块对齐 DeepSeek 官方的峰谷定价时段规则，提供从时段判定、时间换算、模板渲染到多渠道推送、服务端定时调度的完整闭环。它不是简单地显示一张价格表，而是一个能在正确的时间点主动把提醒推送到你面前的自动化服务。

模块定义了两个核心阶段常量：`PVPeak` 表示峰段，`PVValley` 表示谷段。配置和触发记录分别保存在 `peakvalley/config.json` 和 `peakvalley/fired.json`，延续了项目文件即数据库的统一风格。

## 20.2 时区处理的工程难点与解法

峰谷时段是按特定时区定义的，而服务器可能运行在世界任何角落，时区换算是这个模块最棘手的部分。Go 版本可以借助 `time.LoadLocation` 加载 IANA 时区数据库，自动处理全球时区和夏令时。Dart 的 `dart:io` 提供的 `DateTime` 并不内置完整的 IANA 数据库，这是一个真实的能力缺口。

项目没有回避这个差异，而是在注释里如实说明，并给出了行为等价的替代实现：内置本项目支持的 11 个时区的固定偏移规则，覆盖上海、香港、台北、东京、新加坡、首尔、UTC、伦敦、巴黎、纽约、洛杉矶；同时手动实现了欧盟和美国的夏令时规则。

夏令时的计算逻辑写得相当扎实。欧盟规则是三月最后一个周日、十月最后一个周日切换，美国规则是三月第二个周日、十一月第一个周日切换。代码里用 `_nthSunday`（求某月第 n 个周日）和 `_lastSunday`（求某月最后一个周日）两个辅助函数精确计算这些切换日期，再配合欧盟"最后一个周日凌晨一点切换"的具体时点做判断。这样，在支持的 11 个时区范围内，Dart 版本的时段判定结果与 Go 版本完全一致。文档诚实地标注了这是"唯一实现差异"，没有假装两者代码完全相同，这种实事求是的态度值得肯定。

## 20.3 调度机制：30 秒巡检与 10 分钟追补

模块用一组常量清晰地定义了调度行为。`pvTickSeconds` 设为 30，意味着服务端每 30 秒做一次巡检，判断当前是否进入了需要提醒的时段。`pvCatchupMin` 设为 10，是追补窗口：如果服务因为重启等原因错过了精确的触发点，只要还在 10 分钟以内，重启后会补推一次提醒，避免因为短暂停机就漏掉整个峰谷切换通知。

`pvFiredKeep` 设为 2000，表示触发记录最多保留 2000 条。`fired.json` 记录每一次实际推送，用来防止同一个时段被重复提醒。这个有界环形设计避免了记录文件无限膨胀，是长期运行服务必须考虑的细节。`pvMaxBodyBytes` 限制请求体最大 1MB，防止异常超大请求占用内存。

## 20.4 七种推送渠道

峰谷提醒的价值在于"主动送达"。模块支持多达七种推送渠道，覆盖了主流的通知方式，包括 Webhook 通用回调、钉钉机器人、飞书机器人、企业微信、Bark、Server 酱以及系统内通知等。

不同渠道的鉴权方式不同，模块分别做了适配。钉钉和飞书这类要求加签的渠道，使用第十九章提到的纯 Dart HMAC-SHA256 能力对请求签名，确保推送来源可信、不被伪造。每种渠道的消息体格式各不相同，模块通过模板渲染把统一的峰谷提醒内容转换成各平台要求的 JSON 结构，对上层逻辑屏蔽了渠道差异。用户只需在配置里填入对应渠道的密钥和地址，就能选择自己习惯的方式接收提醒。

## 20.5 提醒模板与实际用法

提醒内容通过模板渲染生成，通常包含当前进入的是峰段还是谷段、对应的价格倍率、适合安排的任务类型等信息。典型的使用场景是：用户配置好谷段提醒和推送渠道，当凌晨谷段开始时，手机上自动收到一条通知，提示"当前进入低价谷段，适合执行批量任务"，用户或自动化脚本就可以把文档批处理、大批量翻译、离线数据分析等不急的任务放到这个窗口运行，从而把 API 成本降到最低。

这个模块体现了项目从"能用的聊天界面"向"懂成本、会调度的智能平台"演进的思路。它不追求花哨，而是扎扎实实地解决真实用户在长期高频调用中最关心的省钱问题。

# 第二十一章 TTS 语音合成体系

文字转语音（TTS）让大模型的回答可以被"读出来"，是无障碍使用、语音助手、内容创作场景的重要能力。项目的 TTS 体系由 `tts_edge.dart` 和 `tts_drm.dart` 两个文件构成，对接微软 Edge 浏览器的在线语音合成服务，全程零依赖实现。本章讲解它的工作原理，以及一个关于接口签名升级的真实排障故事。

## 21.1 Edge TTS 的基本工作方式

微软 Edge 浏览器内置了一套高质量的神经网络语音，其背后的合成服务通过 WebSocket 协议对外提供能力。项目没有使用任何封装库，而是直接用 Dart 原生的 WebSocket 客户端与微软的语音服务端点通信。

合成的输出规格固定为 24kHz 采样率、48kbps 码率、单声道 MP3。这是在音质和体积之间取得良好平衡的配置：24kHz 足以清晰表现人声，48kbps 的单声道 MP3 体积小巧，适合网络流式传输和网页即时播放。

## 21.2 文本分块与流式合成

长文本不可能一次性塞进一个合成请求，既可能超出服务长度限制，也会让用户等待太久才听到声音。项目采用"分块合成、边收边写"的流式策略：先把完整文本按句子长度、标点边界切成若干小块，然后逐块发起合成，每收到一块音频数据就立即写入响应流推送给浏览器。

这种设计带来渐进式播放体验：浏览器不需要等整个音频生成完毕，收到前面的数据就可以开始播放，第一句声音的等待延迟非常短。用户感知上是"一点播放就开始朗读"，而不是对着加载转圈等上半天。WebSocket 帧的处理逻辑也很清晰：收到 `Path:audio` 的二进制帧就当作音频数据累积，收到 `Path:turn.end` 就表示当前文本块合成结束，进入下一块。

## 21.3 导致无声的两个真实 Bug 与修复

`tts_edge.dart` 的注释里完整记录了 2026 年修复的两个导致"朗读无声"的真实问题，这是非常宝贵的一线排障资料，值得详细展开。

第一个问题是 DRM 签名算法升级。微软把鉴权用的 `Sec-MS-GEC` 令牌从 v1 版本升级到了 v2 版本。v1 只做一次 SHA-256 摘要，而 v2 要求 CS64 与 SHA-256 双摘要，令牌格式变成 `"2-版本号前缀" + "<16位十六进制CS64>-<64位十六进制SHA256>"`。旧代码还在发 v1 签名，微软服务端直接返回 403 拒绝，于是合成请求全部失败、表现为没有声音。修复方案是在 `tts_drm.dart` 里对齐开源社区 edge-tts 项目的 `drm.py`，完整实现 v2 的双摘要算法，包括一套非标准变体的 SHA-256 常量（初始值、状态常量、调度常量都与标准 SHA-256 不同），并把版本号更新为 `2-143.0.3650.75`。

第二个问题更加隐蔽，是 User-Agent 被污染。Dart 的 `WebSocket.connect` 默认会在你设置的 User-Agent 前面自动拼接一段 `Dart/3.x (dart:io)` 标识。微软的 `speech.platform.bing.com` 端点检测到这个非浏览器 UA 后，判定请求不是来自真实浏览器，同样返回 403。修复方法是使用自定义 HTTP 客户端（customClient），把 userAgent 显式设为 null，从而阻止 Dart 自动拼接标识，只发送一个真实的浏览器 UA，请求这才被正常接受。

这两个 Bug 共同的表现都是"403 错误、朗读无声"，但根因一个在签名算法、一个在请求头，排查时很容易混淆。项目把完整的分析过程写进注释，等于为后来者留下了一份详尽的故障地图。

## 21.4 纯 Dart 实现 DRM 签名的意义

`tts_drm.dart` 里那套非标准 SHA-256 变体，再次体现了零依赖原则的贯彻。为了生成微软要求的特殊签名，项目没有引入加密库，而是根据算法规范手写了专用的哈希实现。受信任令牌 `6A5AA1D4EAFF4E9FB37E23D68491D6F4` 作为常量内置，配合版本号和时间相关参数计算出每次请求所需的动态签名。

需要提醒的是，这类逆向对接第三方非公开接口的方案，天然带有脆弱性：一旦微软再次调整签名算法或鉴权策略，现有实现可能再次失效，需要像 2026 年这次一样跟进更新。项目用详细注释把这种依赖关系和升级历史讲清楚，让维护者能够快速判断"无声"问题是不是又一次接口变更导致的。

## 21.5 TTS 的适用场景与边界

这套 TTS 能力适合的场景包括：把模型回答朗读出来方便视障用户或驾车时使用、把文字稿转成配音音频用于短视频、做成语音播报的通知系统。它的边界也要清楚：它依赖微软的在线服务，需要服务器能访问对应的海外端点，离线环境无法使用；它是通用神经网络语音，情感表达和专业配音演员仍有差距；超长文本要靠分块拼接，极端情况下块与块之间可能有轻微的语气衔接痕迹。认清这些边界，才能把它用在最合适的地方。

# 第二十二章 X（Twitter）推文高速抓取

`xtweet.dart` 实现了对 X（原 Twitter）推文的高速抓取能力，是项目联网信息获取体系的组成部分。它的设计亮点在于"多后端并发竞速"，本章讲解这种架构如何在不稳定的抓取环境里保证成功率和响应速度。

## 22.1 为什么抓取需要多后端

X 平台对非官方数据抓取有严格的反制措施，单一的抓取通道很容易因为限流、鉴权失效、接口调整而失败。如果把所有请求押在一个后端上，一旦它挂了，整个抓取功能就彻底不可用。项目借鉴了高可用系统的思路，同时配置多个抓取后端，用并发竞速的方式对冲单点故障。

## 22.2 并发竞速的工作机制

当用户提交一条推文链接请求抓取时，系统不是依次尝试各个后端（那样太慢），而是同时向所有可用后端发起请求，进入竞速状态。哪个后端最先返回有效结果，就采用哪个的响应，其余请求被取消或忽略。如果某个最快返回的后端报错，系统会等待其他仍在进行的请求，直到拿到第一个成功结果或全部失败。

这种"赛马"模式同时优化了两个指标：成功率上，只要有任意一个后端可用就能拿到数据，避免单点失效；延迟上，最终耗时取决于最快的那个后端，而不是所有后端的平均速度，用户感知到的响应更快。这是用适度的冗余请求换取高可用和低延迟的经典权衡。

## 22.3 结构化的数据模型

抓取成功后，系统把原始返回解析成统一的 `XTweet` 数据对象，字段定义清晰：推文 ID、链接、正文文本、作者用户名、作者显示名、发布时间、媒体附件列表、点赞数、转发数、回复数。

这种统一抽象非常重要。不同后端返回的原始 JSON 结构千差万别，如果把这些差异直接泄漏给上层，前端就要为每个后端写一套适配逻辑。通过在抓取层就归一化成同一个 `XTweet` 模型，上层代码和前端界面只需要面对一种稳定的数据结构，后端的增减、替换对上层完全透明。这是适配器模式在实际项目中的典型应用。

## 22.4 网络层的统一支撑

抓取功能依赖 `net.dart` 提供的统一网络能力，包括带超时控制的 HTTP 请求、自定义请求头、错误分类处理等。统一网络层把连接超时、读取超时、HTTP 状态码异常、DNS 解析失败等各种底层错误，归纳成上层容易处理的错误类型，让竞速逻辑可以干净地判断"这个后端是真的失败了还是只是慢"。

## 22.5 合规与使用边界

抓取第三方平台数据必须重视合规边界。X 的服务条款对自动化抓取有明确限制，这类能力应当用于个人合理范围内的信息查阅，比如快速读取某条公开推文的内容，而不应被用于大规模数据采集、商业转售、绕过平台访问控制等违反条款的用途。项目如实提供技术能力，同时在文档中提醒使用者遵守目标平台的规则和当地法律法规。技术是中性的，使用方式是否正当，取决于使用者自己。

## 22.6 与整体联网体系的配合

X 抓取并不是孤立的功能，它和搜索模块、豆包联网插件、网页抓取能力共同构成项目的信息获取矩阵。当对话中需要引用某条推文时，抓取模块负责把推文内容结构化取回，再交给大模型作为上下文理解和总结。这样模型的回答就能够基于真实的、最新的推文内容，而不是依赖训练数据里可能过时的信息，进一步降低了幻觉风险。

# 第二十三章 会话全文搜索

随着使用时间增长，会话数量会越来越多，从成百上千条历史对话里找到特定内容，就成了刚需。`search.dart` 实现了一套会话全文搜索能力，采用内存缓存加游标分页的设计，本章讲解它的原理与使用。

## 23.1 搜索要解决的真实问题

会话数据分散存储在 `deepseek_chat/sessions/` 目录下的大量文件里，每个会话包含多条消息。如果每次搜索都临时遍历所有文件、读取全部内容，随着数据量上升会越来越慢，磁盘 IO 和 CPU 开销都很大，用户每敲一个关键词都要等待，体验很差。

项目的解法是建立内存缓存：把会话内容加载并索引到内存中，搜索时直接在内存里匹配，避免反复读盘。这是一种用内存换时间的经典策略，在个人和小团队规模的数据量下，内存占用完全可控，而搜索速度可以提升几个数量级。

## 23.2 关键参数与边界保护

代码里用一组常量明确划定了搜索的安全边界，体现了防止滥用的工程意识。

`DsSearchQueryMax` 限制查询关键词最长 500 字符，避免有人提交超长字符串拖垮匹配逻辑。`DsSearchSnippetMax` 规定命中后返回的摘要片段最长 300 字符，既保证用户能看到关键词周围的上下文，又不会让单条结果过于臃肿。`DsSearchLimitMax` 把单次返回上限钉在 200 条，`DsSearchLimitDef` 给出 50 条的默认值，防止一次请求拉取海量结果撑爆内存和网络。

这些硬限制看起来不起眼，却是长期稳定运行的保障。没有它们，一个异常的搜索请求就可能让服务内存暴涨甚至卡死。

## 23.3 命中结果的数据结构

每条搜索命中被封装成 `DsSearchHit` 对象，包含的字段有：会话 ID、会话标题、消息 ID、消息角色（用户还是助手）、摘要片段、是否被截断的标志、时间。

这套字段设计让搜索结果具备完整的可追溯性。用户不仅能看到匹配的文字片段，还知道它来自哪个会话、是谁说的、什么时候说的，点击结果还能通过会话 ID 和消息 ID 直接跳转到原始对话的对应位置。`truncated` 标志则诚实地告诉用户这条摘要因为超过 300 字符被截断了，需要点进去看完整内容，不会让人误以为摘要就是全部。

## 23.4 游标分页机制

搜索结果可能很多，一次性返回既慢又浪费，项目采用游标分页而不是简单的页码分页。游标分页的优势在于它对数据变化不敏感：即使在翻页过程中有新会话写入，也不会出现页码分页常见的"重复一条或漏掉一条"问题。每次请求带上当前游标，系统从游标位置继续向后取固定数量的结果，并返回下一个游标，前端据此实现"加载更多"的滚动体验。

## 23.5 搜索与加密数据的协作

会话内容可能涉及加密存储，搜索模块在读取时会通过 `ds_crypto.dart` 提供的能力正确解密后再纳入索引，保证加密不会影响搜索的可用性。这也意味着搜索索引本身包含敏感明文，应当被当作敏感数据对待。项目把索引放在内存而非落盘，服务重启后重建，客观上减少了敏感索引长期残留的风险，是一个兼顾功能与安全的设计选择。

## 23.6 搜索能力的适用边界

需要客观说明，这套搜索是面向会话场景的轻量全文匹配，并非专业搜索引擎。它擅长关键词级别的检索和上下文摘要，不支持复杂的布尔表达式、相关性排序调优、中文分词的深度优化等高级特性。对于个人知识库规模的会话检索，它的能力绰绰有余；如果未来要面向海量文档做专业级检索，则应当考虑引入专门的倒排索引引擎。项目对自己的能力边界有清晰定位，没有过度设计。

# 第二十四章 文件管理系统

大模型对话经常需要处理文件：上传文档让模型分析、下载模型生成的成果、管理历史附件。`files.dart` 实现了一套完整的文件管理系统，支持最大 5GB 的大文件，核心难点在于分片上传。本章逐层拆解它的设计。

## 24.1 大文件为什么必须分片上传

假设用户要上传一个 5GB 的视频文件让模型理解，如果用普通的单次 HTTP 请求整体上传，会面临一连串问题：请求持续时间极长，任何一次网络抖动都会导致前功尽弃、必须从头重传；服务器要一次性缓冲整个文件，内存压力巨大；浏览器和中间代理对单次请求体大小往往有限制，大请求可能直接被拒绝。

分片上传把大文件切成多个小块（本项目每块 8MB）独立上传，彻底化解了这些问题。每个分片请求小、耗时短，某个分片失败只需重传这一片，不用重传整个文件；服务器逐块接收、逐块落盘，内存占用恒定；还支持暂停后继续、断点续传，用户体验和可靠性都大幅提升。

## 24.2 目录结构与元数据分离

文件系统在 `ds_files/` 下分三个子目录，职责清晰分离。`chunks/` 存放上传过程中的临时分片，`blob/` 存放分片合并完成后的完整文件实体，`meta/` 存放描述文件信息的元数据。

元数据按月分文件，命名为 `ds_file_YYYY-MM.sts`，每个月一个文件。这种按时间分桶的做法避免了单个元数据文件无限膨胀，也方便按月份归档和清理。每条元数据是一行竖线分隔的记录，字段包括：文件 ID、文件名、大小、MIME 类型、分类、创建时间、相对存储路径、来源、关联提示词。文件实体和描述信息分开存储，是成熟文件系统的通用做法——实体文件保持原样便于流式读写，元数据集中管理便于检索和列表展示。

## 24.3 关键常量背后的设计考量

几个常量直接反映了系统的能力定位。`DS_MAX_FILE_SIZE` 设为 5GB，明确支持大视频、大压缩包这类重型文件，呼应了项目"大视频理解"的特色能力。`DS_CHUNK_SIZE` 设为 8MB，是在"分片数量"和"单片重传成本"之间的平衡：分片太小会导致请求数过多、握手开销大，分片太大会让单片失败的重传成本升高，8MB 是实践中比较稳妥的折中值。

两个时间常量体现了资源回收的考量。`DS_UPLOAD_SESSION_TTL` 设为 1 小时：一个上传会话如果超过一小时还没完成，就视为失效。`DS_ORPHAN_GRACE_PERIOD` 设为 30 分钟：合并完成后，临时分片不会立刻删除，而是保留 30 分钟的宽限期，以防合并出现问题时还能回溯，宽限期过后再清理。

## 24.4 分片上传的完整生命周期

一次完整的大文件上传经历这样几个阶段。第一阶段初始化：前端请求创建上传会话，后端生成文件 ID，在 `chunks/` 下准备临时空间，并登记会话的起始时间。第二阶段分片传输：前端把文件切成 8MB 的块，逐块或并发上传，每块带文件 ID 和分片序号，后端按序号落盘，支持失败重传和断点续传。第三阶段合并：所有分片到齐后，前端发起合并请求，后端按序号把分片顺序拼接成完整文件，写入 `blob/`，并校验总大小与元数据声明是否一致。第四阶段登记：生成元数据记录写入当月的 `.sts` 文件，文件正式可用。第五阶段清理：后台的清理定时器（`_uploadCleaner`）周期性扫描，删除超过 TTL 的失效会话分片和过了宽限期的孤儿分片，释放磁盘空间。

## 24.5 孤儿分片与后台清理

网络中断、用户关闭页面、合并失败等情况，都会产生"孤儿分片"——上传没完成、也不会再有人来合并的临时文件。如果不清理，它们会持续占用磁盘。项目用一个后台定时器周期性巡检 `chunks/` 目录，依据会话 TTL 和孤儿宽限期判断哪些分片已经无望完成，安全地回收它们。这个自动垃圾回收机制让文件系统具备了长期无人值守运行的能力，不需要人工定期清理临时目录。

## 24.6 下载、分类与安全

下载接口支持把 `blob/` 里的完整文件以流式方式发回浏览器，配合元数据里的原始文件名和 MIME 类型，浏览器能正确显示文件名和选择打开方式。文件分类字段让用户可以按文档、图片、视频、音频等类型筛选管理。关联提示词字段则记录了这个文件是在哪次对话、为回答什么问题而上传的，建立了文件与会话之间的双向联系。

安全方面，所有文件操作的路径都基于系统生成的文件 ID 和受控的相对路径，避免用户传入任意路径造成目录穿越攻击。文件大小、类型都有相应校验，上传内容被限制在专门的数据目录内，不会污染程序代码。这套文件系统在提供强大能力的同时，守住了最基本的安全底线。

# 第二十五章 模型自动路由

当系统同时接入纯文本模型和视觉模型后，一个隐蔽但严重的问题浮现出来：用户选了纯文本模型，却上传了图片，会发生什么？`model_router.dart` 就是为解决这类问题而生的智能路由层。本章讲解它要解决的真实痛点和三层能力设计。

## 25.1 一个静默失败的真实痛点

要理解模型路由的价值，先看改造前的故障场景。在对话发送链路里，图片并不是直接交给主模型处理的，而是先由一个视觉模型把图片内容提取成文字描述，再把这段描述拼进提示词，最后连同文本一起发给主模型。

改造前的代码在做图片提取时，把用户选择的模型原样透传。这就埋下了一颗雷：如果用户选的是纯文本的 pro 模型，系统就会拿这个"看不见图"的模型去读图，结果必然是提取失败。更麻烦的是，这种失败不是直接报错中断，而是在日志里留下一句"图片内容提取失败"，然后对话继续往下走，只是图片信息悄悄丢失了。用户得到一个完全没理解图片的回答，却不知道问题出在哪。这种"静默降级"是最难排查的故障类型——系统看起来在正常工作，实际能力已经悄悄打折。

## 25.2 三层能力架构

模型路由模块用清晰的三层设计彻底解决这个问题。

第一层是能力判定，函数 `modelSupportsVision()` 负责回答"某个模型到底能不能看图"。它的判断依据有三部分：内置的 DeepSeek 型号能力表，明确标注每个官方型号是否支持视觉；常见第三方视觉型号的名称模式匹配，兼容用户自行接入的其他厂商模型；以及用户在配置文件里自定义的白名单和黑名单，允许人工覆盖自动判断。

第二层是路由决策，函数 `resolveModelRoute()` 是一个纯函数，输入"用户所选模型 + 本轮是否包含图片"，输出"主请求实际用什么模型、图片提取用什么模型、以及为什么这么决策的原因"。纯函数的设计意味着它没有副作用、相同输入永远得到相同输出，非常容易单元测试和推理验证。

第三层是配置与可观测性。路由设置持久化到 `data/deepseek_chat/model_router.sts`，每次路由决策的记录写进一个最多保留 40 条的内存环形缓冲，并通过 `/api/ds-chat/model-router` 接口对外暴露。用户可以随时查看最近的路由决策，搞清楚"我明明选了 A 模型，为什么实际走了 B 模型"。

## 25.3 保守优先的设计哲学

模块在处理未知型号时采取了非常审慎的保守策略：凡是无法确认具备视觉能力的模型，一律按"纯文本"对待。于是当请求里包含图片、而主模型又被判定为纯文本时，路由器会自动把图片提取环节改派给一个视觉兜底模型，而不是冒险把图交给看不见图的模型。

注释里把这个取舍讲得很透彻：宁可多路由一次、付出一点额外开销，也不要把图片交给纯文本模型，因为后者只会产生"图片内容提取失败"的静默降级而不是显式报错，是最难排查的情况。这种"在不确定时选择安全、可观测的那条路"的设计哲学，比单纯追求性能或简洁更值得信赖。

## 25.4 路由记录的可观测价值

那个最多 40 条的内存环形缓冲，是可观测性设计的点睛之笔。多模型系统最容易让用户困惑的就是"实际调用的模型和我选的不一样"。有了路由记录，每一次决策都有据可查：原始选择是什么、是否含图、能力判定结果、最终路由到哪个模型、决策原因是什么，一目了然。当用户反馈"图片理解好像没生效"时，维护者可以直接拉取路由记录，快速判断是能力表配置问题、白黑名单覆盖问题，还是上游图片提取本身的问题，排障效率大幅提升。

## 25.5 与豆包多模型体系的协同

这套路由机制在接入豆包庞大的模型目录后价值更加凸显。豆包体系里既有纯文本的轻量模型，也有支持视觉的多模态模型，还有专门的视频生成、实时语音模型。模型路由器作为统一的调度中枢，能够根据每一轮请求的实际内容（纯文本、含图片、含音频、要生成视频）自动选择最合适的模型，让用户不必记住每个模型的能力边界，也避免了"用错模型导致能力静默失效"的陷阱。它是连接"用户的简单选择"和"复杂模型矩阵"之间的智能缓冲层。

# 第二十六章 实时语音与 RTC 编排

`doubao_realtime.dart` 负责对接火山引擎的端到端实时语音能力，包含全双工实时对话（Seeduplex）和 RTC 音视频互动两部分。这个模块最能体现"服务端代理"架构的必要性，本章详细讲解。

## 26.1 为什么实时语音必须经过服务端代理

实时语音采用 WebSocket 长连接，浏览器和火山引擎语音服务之间需要持续双向通信。一个自然的疑问是：为什么不让浏览器直连火山引擎，而要在中间架一个本地 Dart 服务做代理？注释给出了三个无法回避的技术理由。

第一，浏览器的 WebSocket 构造器无法设置自定义请求头。火山引擎要求在连接握手时通过 `X-Api-Key` 请求头传递密钥，而浏览器原生 WebSocket API 根本不支持自定义头，直连在技术上就走不通。第二，也是安全红线，API Key 绝不能被前端脚本读到。任何写进前端 JavaScript 的密钥，用户打开开发者工具就能看到，等于公开泄露。代理架构让密钥只存在于服务端，浏览器全程接触不到。第三，协议要求一批固定参数，比如实时对话模型版本号 1.2.6.1、采样率 16k 或 24k，由服务端统一补齐，可以避免前端漏填、错填导致的 400 错误。

这三条理由共同决定了代理不是可选项，而是唯一正确的架构。

## 26.2 全双工实时对话的数据流

Seeduplex 全双工意味着用户可以随时打断 AI、双方可以近乎同时说话，体验接近真实人类对话，而不是传统的"说完等对方说完再说"的半双工模式。完整的数据流经这样一条链路：浏览器采集麦克风音频，通过 WebSocket 发给本地 Dart 代理；代理补上鉴权头和固定参数后，转发到火山引擎的 `wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue` 端点；火山引擎做语音识别、理解、语音合成，把返回的音频流再经代理回传给浏览器播放。

代理在中间做的是协议透传和参数补全，本身不做重计算，因此延迟损耗很小，能够维持实时对话所需的低延迟。服务端统一管理连接生命周期、鉴权和错误处理，前端只负责音频的采集和播放，职责划分干净。

## 26.3 RTC AI 音视频互动的服务端编排

模块的第二部分是 RTC（实时音视频）AI 互动，通过 `StartVoiceChat` 和 `StopVoiceChat` 两个动作控制。它的工作方式是：服务端按照火山引擎 V4 签名规范调用 RTC OpenAPI，把端到端语音模型作为一个"AI 参与者"挂载到指定的 RTC 房间里，之后这个 AI 就能像真人用户一样在房间里听和说。

这里有一个必须诚实说明的能力边界，注释里特别强调：服务端只负责"任务编排"这一半，也就是创建、启动、停止 RTC 房间里的 AI 任务。浏览器侧要真正收发 RTC 音视频，还需要集成火山引擎官方的 RTC Web SDK 来处理音视频轨道、房间连接等客户端工作。项目明确要求前端不得谎称已经能够独立完成通话，这种对能力边界的诚实标注，避免了使用者产生不切实际的预期，是负责任的工程态度。

## 26.4 V4 签名与安全

调用 RTC OpenAPI 需要火山引擎的 V4 签名机制，这是一套比简单 API Key 更严格的请求签名方案，把请求方法、路径、时间戳、密钥等要素组合计算出签名，防止请求被篡改或重放。签名过程在服务端完成，涉及的 Secret Key 同样不会暴露给前端。这与实时语音代理的安全模型一脉相承：所有敏感凭证和签名逻辑都收敛在服务端，浏览器只持有与本地代理之间的临时连接。

## 26.5 零依赖与如实上报原则

整个实时语音模块延续了项目的两条核心原则。其一是零第三方依赖，WebSocket 通信、HTTP 调用、签名计算全部用 Dart 标准库和项目自有工具完成，没有引入实时通信 SDK 的服务端重型依赖。其二是失败一律如实上报，无论是握手失败、鉴权被拒、参数错误还是上游连接中断，模块都会把真实错误返回给前端，而不是吞掉异常、假装连接正常。在实时通信这种链路长、故障点多的场景里，如实上报是快速定位问题的前提，也与全项目"不伪造成功"的工程诚信保持一致。

## 26.6 实时语音的典型应用

这套能力支撑的典型场景包括：语音助手式的自然对话，用户直接说话提问、AI 语音回答；无障碍交互，为不便打字或视障用户提供纯语音操作路径；以及 RTC 房间里的 AI 陪练、AI 主持人、虚拟客服等需要 AI 作为实时参与者的应用。理解了"服务端代理保安全、官方 SDK 管客户端"的分工，就能在二次开发时正确地把这套实时能力接入自己的产品，而不会在架构上走弯路。

# 第二十七章 多语言国际化体系

项目面向多国家用户，内置了一套覆盖六种语言的国际化（i18n）体系。本章讲解它的目录组织、翻译机制、源语言约定，以及在新增内容时如何正确地维护多语言。

## 27.1 支持的语言与目录结构

国际化资源集中在根目录的 `i18n/locales/` 下，目前支持六种语言：日语（ja）、简体中文（zh）、英语（en）、韩语（ko）、俄语（ru）、法语（fr）。每种语言对应两个文件，例如日语有 `ja.js` 和 `ja-extra.js`，英语有 `en.js` 和 `en-extra.js`，其余语言同理。

把每种语言拆成主文件和 extra 文件，是一种职责分离的设计。主文件存放界面常规文案的翻译，extra 文件专门存放后端 Dart、Python 报错信息等补充文案的翻译。这样当后端新增错误提示时，只需要更新各语言的 extra 文件，不必改动体量较大的主文件，降低了合并冲突的概率，也让翻译维护的边界更清晰。

## 27.2 以日语为 key 的翻译机制

这套 i18n 有一个不同寻常但自洽的设计：它以日语文案作为翻译字典的 key。也就是说，代码和界面里默认写的是日语原文，翻译函数 `T()` 接收日语文本，再去当前语言的字典里查找对应的译文。

这种设计的好处是省去了一层抽象的消息 ID。很多 i18n 方案要求开发者先定义一个类似 `app.button.submit` 的语义化 key，再在每个语言文件里为这个 key 填译文，开发者面对代码时看到的是抽象 ID 而非真实文案。本项目直接用日语原文当 key，开发者在代码里看到的就是可读的真实文字，理解成本更低；日语本身作为源语言，不需要任何翻译条目，字典里查不到时就原样返回日语，天然具备兜底能力。

## 27.3 翻译函数的兜底逻辑

翻译函数 `T()` 的运行逻辑可以概括为"查表、命中则译文、未命中则原文"。当界面需要显示一段文字时，调用 `T(日语文案)`，函数根据当前选定的语言，打开对应语言的字典查找：如果找到了匹配的日语 key，就返回该语言的译文；如果没找到，直接返回传入的日语原文。

这套兜底逻辑保证了系统永远不会因为缺少翻译而显示空白或报错。哪怕新增了一个界面元素却暂时只写了日语、其他五种语言还没来得及翻译，界面也能正常显示日语原文，功能完全可用，只是该条文案尚未本地化。这让多语言维护可以渐进式推进，而不要求每次改动都一次性补齐六种语言。

## 27.4 模型标签的翻译实践

模型名称这类条目的翻译有专门的约定，体现了专有名词处理的规范性。以视频模型为例，日语源标签写成 `Doubao-Seedance-2.5（次世代動画生成・4-30秒・4K対応）` 这样的形式，其中模型的拉丁字母标识 `Doubao-Seedance-2.5` 是专有名词，在所有语言里都保持原文不翻译，只有括号内的功能说明部分被翻译成对应语言。

这样处理兼顾了两个目标：一是保证模型 ID、产品名这类技术标识在全球范围内完全一致，避免翻译造成的混淆和对接错误；二是让不同语言的用户都能读懂括号里的功能介绍。新增模型时，需要在日语源里定义标签，再到 zh、en、ko、ru、fr 五个语言文件里各补一条翻译，日语本身无需条目。

## 27.5 新增界面文案的正确流程

基于上述机制，二次开发新增一段需要国际化的界面文案时，正确流程是：第一步，在代码里用日语写出源文案；第二步，到五个非日语语言文件的字典里，分别添加"日语文案 → 对应语言译文"的条目；第三步，如果是后端报错类文案，放进对应语言的 extra 文件而不是主文件；第四步，验证切换到每种语言时文案正确显示，并确认漏翻时能正常回退到日语。

维护时要特别注意字典 key 必须和代码里的日语原文逐字一致，包括标点、空格、全角半角，任何细微差异都会导致查表失败而回退原文。这是以自然语言当 key 的方案需要格外留心的地方。

## 27.6 国际化体系的适用边界

六语言覆盖加上渐进式翻译兜底，对个人和中小团队的多语言产品已经相当完备。它的边界在于：这是一套基于静态字典的前端国际化方案，适合界面固定文案的翻译，并不处理复杂的复数规则、性别变位、语序重排等深层本地化问题，也没有集成专业的翻译管理平台。如果未来要支撑几十种语言、需要专业翻译团队协作和动态语言包下发，才需要考虑更重型的 i18n 框架。以当前项目的规模和定位，这套轻量方案在简洁与实用之间取得了恰当的平衡。

# 第二十八章 前端架构与交互模块

项目前端坚持纯原生技术栈，不依赖 React、Vue 等框架，也没有打包构建步骤，所有 JavaScript 和 CSS 文件直接由浏览器加载。本章梳理根目录下各个前端模块的职责，以及这种朴素架构带来的实际好处。

## 28.1 纯原生技术栈的取舍

打开项目根目录可以看到，前端由一批独立的 `.js` 和 `.css` 文件组成，通过 `index.html` 直接引入。没有 node_modules、没有 webpack 或 vite 配置、没有 JSX 或单文件组件，全部是浏览器原生支持的 JavaScript 和 CSS。

这种选择和后端的零依赖哲学一脉相承。好处非常实际：第一，开箱即用，克隆下来用静态服务器或后端托管就能跑，不需要 `npm install` 和漫长的构建；第二，没有框架版本升级带来的破坏性变更，代码不会因为框架过时而过期；第三，调试直接，浏览器里看到的就是源码本身，问题定位路径短。代价是缺少框架提供的组件化和状态管理能力，复杂界面需要手动操作 DOM，对开发者的原生 JS 功底要求更高。项目用清晰的模块拆分弥补了这一点。

## 28.2 核心前端模块职责

根目录下的前端文件按功能高度内聚，每个模块负责一块独立能力。

`dsc-doubao.js` 和 `dsc-doubao.css` 是豆包功能的核心前端，负责模型目录渲染、对话界面、视频生成、联网插件开关等豆包相关交互，模型下拉框通过调用后端的 `modelsByCat('video')` 等接口动态获取，后端新增模型后前端自动展示，无需硬编码。`dsc-doubao-tools.js` 专门处理工具模式的界面逻辑。`deepseek-chat.js` 和 `deepseek-chat.css` 承载 DeepSeek 对话主界面。`dsc-duplex.js` 负责全双工实时语音的前端音频采集与播放。`dsc-model-route.js` 提供模型自动路由的可视化配置和路由记录查看。

生态功能各有专属模块：`dsc-forum.js` 与 `dsc-forum.css` 实现论坛界面，`dsc-announcements.js` 负责公告展示，`dsc-vocab.js` 与 `dsc-vocab.css` 实现单词本学习界面，`ds-files.js` 与 `ds-files.css` 处理文件管理和分片上传，`ds-devtools.js` 与 `ds-devtools.css` 提供开发者工具，`peakvalley.js` 与 `peakvalley.css` 实现峰谷提醒配置界面。

## 28.3 体验增强类小模块

除了业务模块，还有一批专注交互细节的轻量模块，体现了对使用体验的打磨。

`dsc-swipe.js` 实现移动端的滑动手势，让手机用户可以通过左右滑动切换会话或功能页，贴合原生 App 的操作习惯。`dsc-menu-scroll.js` 处理菜单的滚动行为，保证导航项较多时菜单依然顺滑可用。`dsc-newline-fx.js` 为换行和消息出现添加视觉动效，提升对话的生动感。`dsc-ja-fix.js` 是针对日语显示的专项修复，处理日语排版、换行规则等语言特有的界面问题。这些模块各自很小、职责单一，组合起来却显著改善了整体手感。

## 28.4 数学公式与语音渲染

根目录的 `tex-chtml-full-speech.js` 是一个值得注意的专用组件，用于把 LaTeX 数学公式渲染成可视化的 HTML（chtml），并兼顾语音朗读场景。大模型在解答数学、物理、化学问题时经常输出公式，这个组件保证公式在网页上正确排版，而不是显示成一串难以阅读的原始 LaTeX 代码。它与 TTS 能力配合，还能让公式内容被合理地朗读出来，服务于无障碍和语音交互。

## 28.5 前后端的通信约定

前端所有动态数据都通过后端暴露的 HTTP 接口获取，遵循统一的通信约定：接口返回结构化 JSON，前端负责渲染；写操作通过 POST 或 multipart 提交，后端处理后返回成功状态或错误信息；实时能力（如全双工语音）走 WebSocket。前端不直接持有任何 API Key，所有敏感凭证和第三方签名都由后端代理，这一安全约束在实时语音章节已经详细说明，前端架构同样严格遵守。

错误处理上，前端会如实展示后端返回的错误信息，配合 i18n 的 extra 文案把后端报错本地化。这种"后端如实报错、前端如实呈现"的闭环，让用户看到的失败信息是真实可排查的，而不是被模糊处理的"操作失败"。

## 28.6 朴素架构的长期价值

在前端工程化日益复杂、依赖链动辄上千个包的当下，这套纯原生、零构建的前端显得有些"复古"，但它换来了极强的可移植性和可维护性。任何一个静态空间都能托管，任何一个懂基础 JavaScript 的开发者都能读懂和修改，不存在构建工具链失效、框架停止维护的风险。对于一个强调长期稳定、个人可控、数据自主的项目而言，这种朴素不是能力不足，而是一种经过权衡的、清醒的技术选择。后端零依赖、前端零构建、数据全在本地文件，三者共同构成了这个项目"极简而完整"的技术底色。

# 第二十九章 HTTP 服务与路由总览

整个后端的对外能力都通过一个内置 HTTP 服务器暴露，`httpsrv.dart` 是这个服务器的核心，负责接收请求、路由分发、静态文件托管和统一响应。本章从整体上讲解请求是如何被处理的，帮助你在二次开发时快速定位该去哪里加接口。

## 29.1 内置 HTTP 服务器的意义

项目没有使用 shelf、dio 之类的第三方 Web 框架，而是基于 Dart 标准库的 `HttpServer` 自建服务。这依然是零依赖原则的延续：不把整个系统的运行寄托在某个外部 Web 框架上，路由、响应、静态托管全部自己掌控。自建服务器虽然要多写一些基础代码，但换来的是完全透明的请求处理流程和极小的运行时 footprint。

服务器启动后监听指定端口，浏览器访问根路径时返回 `index.html`，随后前端的各类 JS、CSS、图片等静态资源也由同一个服务器托管。这意味着整个产品可以用单进程、单端口完整提供服务，部署时不需要额外配置 Nginx 之类的反向代理（当然生产环境前面加一层反向代理做 TLS 终止依然是推荐做法）。

## 29.2 路由分发的组织方式

路由层把不同前缀的请求分发给对应模块的处理函数。整体可以分成几大类：

第一类是对话相关接口，处理 DeepSeek 和豆包的消息发送、会话管理、模型列表、模型路由等，是系统的核心流量。第二类是文件相关接口，处理分片上传、合并、下载、元数据查询。第三类是生态功能接口，对应论坛、公告、单词本、自定义模型、峰谷提醒、备份恢复等模块。第四类是实时通信接口，处理 WebSocket 升级，服务全双工语音。第五类是静态资源请求，返回前端文件。

每个处理函数遵循统一的签名约定，接收请求对象、解析参数、调用对应业务模块、最后通过统一的响应工具返回 JSON 或二进制数据。这种一致性让新增接口的套路非常固定，二次开发时照着现有接口仿写即可。

## 29.3 统一响应与错误格式

为了让前端能用统一的逻辑处理结果，后端约定了一致的响应结构。成功响应通常包含状态标志和业务数据，失败响应包含错误码和可读的错误信息。错误信息会配合 i18n 的 extra 文案在前端本地化，因此同一个后端错误，日语用户看到日语、中文用户看到中文。

统一响应格式的价值在项目规模变大后尤其明显。前端可以写一个通用的请求封装，集中处理鉴权失效、参数错误、服务器异常等情况，而不必为每个接口单独写一套判断逻辑。后端也能在一个地方统一记录访问日志和错误日志，便于排障。

## 29.4 请求体大小限制与防护

在峰谷、搜索、文件等章节已经看到多个 `MaxBodyBytes` 之类的常量，这种对请求体大小的限制是 HTTP 层重要的防护手段。如果不限制请求体大小，恶意或异常的超大请求可能耗尽服务器内存。各个接口根据自身业务特点设定合理上限：普通 JSON 接口限制在较小范围，文件上传则走专门的分片通道、单片大小受控，而不是放开整体请求体。

这种"默认收紧、按需开口"的防护思路，配合文件模块的路径校验、加密模块的密钥管理，共同构成了系统的基础安全防线。虽然项目定位是个人和小团队使用，但并没有因此放弃基本的安全卫生。

## 29.5 静态资源与前端托管

HTTP 服务器同时承担前端静态资源托管职责。请求命中实际存在的静态文件时，服务器根据扩展名设置正确的 Content-Type，例如 JavaScript 返回 `application/javascript`、CSS 返回 `text/css`、图片返回对应图片类型，再把文件内容流式返回。正确的 MIME 类型是浏览器正常解析和执行前端资源的前提。

对于不存在的路径，服务器返回合适的 404 响应而不是崩溃。单页应用常见的"前端路由刷新 404"问题，也可以在这一层通过回退到 index.html 解决。静态托管和 API 共用同一端口、同一服务，让部署形态保持极简。

## 29.6 如何新增一个后端接口

基于上述架构，新增接口的标准路径很清晰。第一步，在对应业务模块（或新建模块）里写好处理函数，遵循统一签名和响应约定。第二步，在路由分发处注册新的路径和方法，把它指向你的处理函数。第三步，如果是敏感操作，复用现有的加密和鉴权工具，不要自行处理密钥。第四步，前端在对应 JS 模块里调用新接口，并按统一响应格式处理结果。第五步，若有面向用户的新文案，按 i18n 章节的流程补齐六种语言。整个过程不需要改动框架核心，只在业务层扩展，体现了良好的可插拔性。

# 第三十章 网络层与错误处理

`net.dart` 是所有对外 HTTP 通信的统一底座，DeepSeek、豆包、Edge TTS、X 抓取等模块发起的网络请求都建立在它之上。本章讲解统一网络层带来的价值，以及项目贯穿始终的错误处理哲学。

## 30.1 为什么需要统一网络层

如果每个业务模块各自用 `HttpClient` 发起请求，会导致大量重复代码：设置超时、拼装请求头、处理状态码、解析 JSON、分类错误，这些逻辑会散落各处，一旦要调整（比如统一加一个请求头、修改超时策略），就得改很多地方，极易遗漏。

统一网络层把这些共性能力收敛到一处。上层模块只需表达"我要请求哪个 URL、用什么方法、带什么头和体"，底层统一负责连接管理、超时控制、响应读取和异常包装。这既减少了重复代码，也保证了全项目网络行为的一致性。

## 30.2 超时控制的重要性

网络请求最大的不确定性在于对端可能无响应。如果不设超时，一个挂死的连接会长时间占用资源，极端情况下大量挂死请求会耗尽连接池和内存，让整个服务失去响应。统一网络层为连接、读取等阶段设置明确的超时，保证任何请求在约定时间内要么成功、要么失败返回，不会无限期等待。

不同场景对超时的容忍度不同：普通 JSON 对话接口要求快速响应，超时设得较短；大文件下载、实时语音这类长连接场景则需要更长或独立的超时策略。统一网络层提供可配置的超时参数，让各模块按自身特点选择，而不是一刀切。

## 30.3 错误分类与如实上报

网络错误的种类很多：DNS 解析失败、连接被拒、TLS 握手失败、读取超时、对端返回 4xx/5xx 状态码、响应体不是合法 JSON……如果把这些统统包装成一句模糊的"请求失败"，排障时几乎无从下手。

项目的网络层对错误做了明确分类，把底层异常转换成携带真实原因的错误对象向上抛出。是超时就说是超时，是 403 鉴权失败就保留 403 和对端返回信息，是 JSON 解析失败就指出是响应格式问题。TTS 章节里那两个 403 故障之所以能被精准定位到签名算法和 User-Agent，正是因为网络层如实保留了状态码和响应细节。这种"失败一律如实上报、不吞异常、不伪造成功"的原则，是全项目一以贯之的工程诚信。

## 30.4 自定义请求头与浏览器伪装

在对接 Edge TTS、X 抓取这类非官方或有反制措施的接口时，请求头的设置至关重要。TTS 的案例已经展示过：Dart WebSocket 默认拼接的 UA 会导致 403，需要用自定义客户端规避。统一网络层支持灵活设置请求头，让各模块能够按目标服务的要求构造 UA、鉴权头、内容类型等，把这类"接口特化"的细节集中管理。

同时要强调，自定义请求头能力必须被合规使用。设置合理的 UA 以正常访问公开接口是正当的技术手段，但伪造身份、绕过访问控制、违反目标平台服务条款则不可取。项目提供能力，使用者需自行承担合规责任。

## 30.5 重试策略的取舍

网络请求失败后是否自动重试，需要谨慎权衡。幂等的 GET 请求在遇到临时性网络抖动时，适度重试可以提升成功率；但非幂等的写操作（比如发送消息、创建订单）盲目重试可能造成重复提交。统一网络层在设计重试时区分请求性质，对适合重试的场景限制重试次数并加入退避间隔，避免在对端已经过载时还用密集重试雪上加霜。

对于竞速抓取这类本身就有多后端冗余的场景，重试更多体现为"切换后端"而不是"死磕同一个后端"，这在 X 抓取章节已经讲过。统一网络层提供的错误分类，正是上层决定"该不该重试、换谁重试"的决策依据。

## 30.6 错误处理的整体哲学

纵观加密、TTS、文件、实时语音各章，可以提炼出项目对待错误的统一哲学：第一，尽早失败，发现参数非法、状态不符就立即报错，而不是带着错误状态继续运行；第二，保留现场，错误信息尽量包含状态码、原因、上下文，方便事后定位；第三，如实传递，不在中间层把具体错误吞掉换成模糊提示；第四，区分可恢复与不可恢复，临时性故障可重试或降级，确定性错误（如鉴权失败、参数错误）应直接暴露让用户修正。

这套哲学让系统在长期无人值守运行时具备良好的可观测性和可维护性。一个会诚实告诉你"我哪里坏了"的系统，远比一个看似从不报错、实则静默出错的系统值得信赖。网络层作为所有对外通信的咽喉，正是实践这套哲学的第一道关口。

# 第三十一章 Token 计费与用量统计

大模型按 Token 用量计费，用了多少、花了多少钱，是用户最关心的实际问题之一。`ds_usage.dart` 负责用量统计，配合各模型目录里的单价信息，构成项目的计费与用量追踪体系。本章讲清楚 Token 的概念、统计口径和成本控制方法。

## 31.1 什么是 Token

Token 是大模型处理文本的最小单位，可以理解为"词元"。它不等于一个汉字，也不等于一个英文单词，而是模型分词器切分出来的片段。常见规律是：英文里一个常见单词约等于一个或几个 Token，中文里一个汉字通常对应一到两个 Token，标点、空格、代码符号也各自占用 Token。

一次 API 调用的计费通常分两部分：输入 Token（你发给模型的所有内容，包括系统提示词、历史对话、附件提取文本）和输出 Token（模型生成的回答）。两者单价不同，输出 Token 一般比输入 Token 贵。理解这一点，才能明白为什么冗长的系统提示词和不加裁剪的历史对话会悄悄推高成本。

## 31.2 用量统计的实现思路

用量模块在每次对话请求返回后，从响应里读取平台回传的 Token 用量字段，分别记录输入、输出数量，结合所调用模型的单价，计算本次调用的费用，并按时间、模型、会话等维度累积存储。统计数据同样落在 `data/` 目录下，遵循文件即数据库的统一设计，方便备份和迁移。

把用量数据和会话关联起来，用户就能回答这类实际问题：这个月哪个会话最烧钱、哪个模型调用最频繁、输入和输出的占比如何。相比只在平台后台看一个总账单，项目内的细粒度统计更能帮助用户定位成本来源。

## 31.3 豆包模型的真实计费口径

以项目重点推荐的豆包 Seed 2.1 Lite 为例，其计费按每百万 Token 计价，输入和输出分别定价。用户实际承担的成本，等于输入 Token 数乘以输入单价、加上输出 Token 数乘以输出单价。需要强调的是，具体单价以火山引擎官方控制台和合同档位为准，项目内配置的价格应与官方保持同步，官方调价后要及时更新模型目录里的单价，否则统计出的费用会与真实账单产生偏差。

免费额度也是成本规划的重要部分。新用户通常有一定规模的免费 Token 额度，测试阶段应优先利用免费额度完成功能验证，正式上线跑量后再按实际消耗结算。用量统计模块能帮助你清楚区分"免费额度内"和"付费区间"的消耗。

## 31.4 影响成本的关键因素

结合输入输出分别计费的机制，可以梳理出几个直接影响成本的因素。第一是上下文长度，每次请求都会把历史对话重新作为输入发送，长对话的输入 Token 会随轮次累积膨胀，适时裁剪历史、做摘要压缩能显著省钱。第二是输出长度，无节制地要求模型长篇大论会快速消耗较贵的输出 Token，合理设定最大输出长度很有必要。第三是模型选择，旗舰模型单价高、轻量模型单价低，用模型路由器把简单任务分派给轻量模型、复杂任务才动用旗舰模型，是控制总成本的有效手段。第四是工具调用，联网搜索、图片理解等会引入额外的输入内容或独立计费，需要按需触发而不是默认全开。

## 31.5 结合峰谷的成本优化

用量统计与第二十章的峰谷提醒可以联动，形成更完整的成本控制闭环。对于不要求即时完成的批量任务——比如批量翻译、长文档摘要、离线数据分析——可以安排在低价谷段执行，用时间换价格。用量模块负责事后核算实际花费，峰谷模块负责事前提醒窗口，两者配合让用户对"花了多少、什么时候花最省"都心中有数。

## 31.6 统计数据的正确定位

需要明确，项目内的用量统计是帮助用户自我管理的参考值，最终计费始终以模型平台官方账单为准。两者可能因为 Token 计数口径、免费额度抵扣、四舍五入、汇率或档位折扣等原因存在细微差异。正确的用法是：用项目内统计做日常的成本监控和趋势分析，用平台官方账单做最终的财务对账。文档不夸大本地统计的权威性，这种诚实定位能避免用户在对账时产生误解。

# 第三十二章 自动化脚本与辅助工具

除了 Dart 后端和网页前端，项目根目录还附带一批 Python 和 Shell 脚本，承担环境准备、权限维护、自动化运行等辅助职责。本章讲解这些脚本的作用，以及它们如何与主程序配合形成完整的运行体系。

## 32.1 脚本清单与分工

根目录下的辅助脚本各有明确分工。`adb_up.sh` 是 Shell 脚本，用于在安卓环境下建立和恢复 ADB 无线调试连接，是自动化操作安卓设备的前置准备。`auto.py`、`doubao_auto.py` 是 Python 自动化脚本，承担流程编排和自动执行的职责。`ha.py`、`st.py` 则分别对应特定的辅助任务，配合主系统完成特定场景的自动化。

这些脚本与 Dart 主程序是协作关系而非替代关系：Dart 负责核心的 HTTP 服务、模型对接和数据管理，Python/Shell 脚本负责主程序之外的环境维护、设备控制和定时自动化，各取所长。Dart 适合构建稳定的长期服务，Python 适合快速编写自动化逻辑，Shell 适合直接调用系统能力，三者组合覆盖了完整的运维需求。

## 32.2 ADB 无线调试的作用

在安卓设备（尤其是 Termux 环境）上运行这类自动化系统时，经常需要通过 ADB（安卓调试桥）执行输入、启动应用、读取系统状态等操作。`adb_up.sh` 把连接无线 ADB 的步骤封装起来，确保设备上的 ADB 通道处于可用状态。无线调试避免了 USB 线的束缚，让设备可以在无人值守的情况下长期被远程控制。

这类脚本通常包含连接到本地 ADB 端口、检查连接状态、必要时重新建立连接的逻辑。把这些容易出错、需要重复执行的命令固化成脚本，既减少了人工操作，也让自动化流程可以在连接意外断开后自行恢复，提升长期运行的稳定性。

## 32.3 Python 自动化的定位

`auto.py` 和 `doubao_auto.py` 体现了把大模型能力接入自动化流程的思路。它们可以按照预设逻辑，周期性或触发式地调用主系统提供的接口，完成诸如自动对话、批量任务、状态巡检等工作。Python 生态在自动化、定时调度、数据处理方面库丰富、编写灵活，适合承载这类"胶水"逻辑。

需要注意的是，自动化脚本在调用涉及付费模型的接口时，同样受 Token 计费和联网插件计费规则约束。无人值守的自动化如果不加控制，可能因为逻辑循环或异常重试产生意料之外的费用。因此脚本层面应当设置调用频率上限、费用阈值和失败熔断，与第三十一章的用量统计配合，做到自动化但不失控。

## 32.4 脚本与主系统的安全边界

辅助脚本往往拥有较高的系统权限（ADB 可以控制设备输入和应用），使用时必须清楚其安全边界。第一，脚本应只在受信任的本地环境运行，不要把具备设备控制能力的接口暴露到公网。第二，脚本里不应硬编码 API Key 等敏感凭证，应复用主系统的加密配置或通过环境变量注入。第三，自动化操作要避免不可逆的危险动作，涉及删除、发送、支付等操作时保留人工确认环节。

主系统通过加密、路径校验、请求体限制构建的安全防线，不能因为一个权限过大、缺乏约束的脚本而被绕过。脚本是能力的放大器，既放大效率，也放大风险，规范使用至关重要。

## 32.5 长期无人值守的运行建议

结合脚本能力和前面各章的机制，给出长期无人值守运行的几条建议。其一，用进程守护或定时任务保证主程序和关键脚本在崩溃、重启后能自动拉起。其二，善用 ADB 脚本的自愈能力，定期检查设备连接状态，断了自动重连。其三，配置备份策略，让 `data/` 目录定期打包并异地保存，防止设备故障导致数据丢失。其四，设置用量和费用告警，避免自动化失控造成高额账单。其五，关注日志，主系统如实上报错误的设计需要配合定期的日志巡检才能发挥价值，及时发现静默异常。

## 32.6 二次开发脚本的规范

如果要自行扩展自动化脚本，建议遵循项目已有的工程规范：脚本职责单一、命名清晰、与主系统通过明确的 HTTP 接口交互而不是直接读写内部数据文件；敏感信息走环境变量或加密配置；所有外部调用做好超时和错误处理，失败如实记录；涉及计费的操作加上频率与费用约束。保持这些规范，新增脚本就能无缝融入现有体系，而不会成为难以维护的"野代码"。这套"Dart 核心服务 + Python 自动化 + Shell 系统操作"的多语言协作模式，正是项目在真实复杂环境中打磨出来的实用架构。

# 第三十三章 性能调优与资源优化

## 33.1 性能调优的总体思路

本项目运行在资源相对有限的移动设备或轻量服务器上，性能调优的核心不是追求极限吞吐，而是在有限的内存、CPU、网络和电量约束下，保证对话响应及时、长任务不中断、后台不被系统回收。调优要建立在对真实瓶颈的测量之上，而不是凭感觉改参数。本章按照"先测量、再定位、后优化"的顺序，结合项目各模块的真实实现，给出可落地的优化方向。

性能问题通常分为四类：第一类是网络延迟，表现为首字响应慢、流式输出卡顿，瓶颈往往在到模型网关的连接或联网插件检索；第二类是 CPU 与内存压力，表现为设备发热、界面卡顿、进程被系统杀死，常见于大文件处理、长上下文拼装、加密解密密集场景；第三类是存储 I/O，表现为读写历史、备份打包、全文索引时变慢，多与数据文件膨胀、频繁同步落盘有关；第四类是并发与锁竞争，表现为多个请求互相等待、队列堆积，需要审视异步调度和共享资源的访问方式。

## 33.2 网络层优化

网络是对话类应用最主要的延迟来源。项目的网络层在 `net.dart` 中统一封装了超时、重试和错误归一化逻辑，调优首先要合理设置超时时间。连接超时不宜过长，否则在网络异常时用户会长时间面对无响应界面；也不宜过短，否则弱网下正常请求被误判失败。读取超时则要区分场景：普通对话可以设置较短的读取超时快速失败，而长文本生成、深度思考、视频生成这类天然耗时的任务，需要更长的读取超时或改用异步任务轮询，避免中途被掐断。

流式输出（SSE）是降低体感延迟的关键手段。相比等待完整响应一次性返回，流式输出可以在模型生成第一个 Token 时就把内容推给前端，首字延迟从"整段生成时间"降低到"首 Token 时间"，体感提升非常明显。项目的对话接口默认采用流式返回，前端逐段渲染。调优时要确保中间的代理、网关没有缓冲 SSE 数据，否则流式会退化成"伪流式"，失去降低首字延迟的意义。

连接复用是另一个重要优化点。频繁建立 HTTPS 连接会产生 TCP 握手和 TLS 协商开销，在高频对话场景下累积明显。项目通过统一的网络客户端复用底层连接池，让多次请求共享已建立的连接。部署时如果前置了 Nginx 等反向代理，也要开启 keepalive，避免代理到后端之间反复建连。

重试策略需要兼顾可用性与成本。网络抖动时适度重试可以提升成功率，但对计费接口而言，盲目重试可能导致重复扣费或重复生成。项目的重试逻辑区分错误类型：连接失败、网关超时这类没有真正到达模型的错误可以安全重试；而已经进入生成阶段、返回了部分内容的请求，重试前要确认上一次请求是否已经计费，避免重复消耗。指数退避配合最大重试次数，是兼顾稳定与成本的稳妥做法。

## 33.3 内存与上下文优化

大模型应用的内存压力很大程度来自上下文拼装。随着对话轮次增加，历史消息、系统提示词、联网检索结果、工具返回内容会不断累积，如果不加控制地全部塞进每次请求，不仅内存占用上升，输入 Token 费用也会快速增长，还可能超出模型的上下文窗口。项目在对话模块中对历史消息做了分层管理：近期消息完整保留，较早的历史可以摘要压缩或按策略截断，在保持对话连贯性的同时控制每次请求的体积。

调优建议之一是合理设置历史轮次上限。对于日常问答，保留最近十几到二十轮通常足够维持上下文，更早的内容可以在需要时通过跨会话引用、全文搜索按需召回，而不是常驻上下文。之二是对联网检索和工具返回的内容做裁剪：搜索结果往往包含大量网页噪声，只提取与问题相关的片段注入上下文，既省 Token 又降低干扰。之三是关注大文件处理的内存峰值，读取大文件、解析长文档时采用分块处理而非一次性全量载入，避免瞬时内存冲高触发系统回收。

图片、音频等多模态内容的内存占用同样需要关注。图片在送入多模态模型前应按模型要求压缩到合适分辨率，过大的原图既增加上传流量和 Base64 编码体积，也没有识别精度上的必要收益。音频和视频理解走的是专门的分片与上传流程，调优时要确保临时文件及时清理，避免长期占用存储空间。

## 33.4 存储与 I/O 优化

随着使用时间增长，`data/` 目录下的历史记录、会话文件、全文索引、备份包会持续膨胀，存储 I/O 逐渐成为瓶颈。第一层优化是控制单次写入的粒度和频率。对话历史的落盘要在"及时持久化防止丢失"和"避免每条消息都同步刷盘"之间平衡，项目通常采用消息完成或阶段性节点写入的策略，既保证异常退出后数据基本不丢，又不至于让磁盘 I/O 过于频繁。

第二层优化是善用备份的归档与清理机制。`backup.dart` 提供的备份功能会把数据目录打包，备份包应配合保留策略定期清理过期版本，否则备份文件本身会吃掉大量空间。建议把备份目录与活跃数据目录分开存放，有条件时异地保存，既缓解本地空间压力，又提升容灾能力。

第三层优化针对全文搜索。`search.dart` 的索引需要在写入新内容时增量更新，随着可搜索内容增多，索引体积和检索耗时都会上升。调优时要为索引设置合理的字段范围，只对真正需要检索的文本字段建索引，避免把大块无关数据纳入。定期重建索引可以回收删除内容残留的空间、整理碎片，在数据大量变动后效果明显。

## 33.5 并发与异步调度

Dart 的事件循环和异步机制是项目处理并发的基础。所有涉及网络、文件、加密的耗时操作都以异步方式执行，避免阻塞主事件循环。调优的关键在于不要在主 isolate 中执行长时间的同步计算，遇到大文件哈希、批量加密、复杂数据处理这类 CPU 密集任务时，应通过独立 isolate 分担，保证主循环能够及时响应新的请求和 UI 事件。

共享资源的访问需要谨慎处理并发。多个请求可能同时读写同一份配置、历史或用量统计文件，如果缺乏协调会出现数据覆盖、读到中间状态等问题。项目通过有序的异步调度和必要的锁机制，把对关键共享文件的访问串行化或原子化。调优时要避免锁粒度过大导致吞吐下降，也避免完全无锁导致竞争，按资源的实际争用程度选择合适的同步方式。

写入配置和统计数据时，原子写入是防止文件损坏的有效手段：先写到临时文件，确认完整后再原子替换目标文件，这样即使写入过程中断电或崩溃，也不会留下半个损坏的文件。项目在关键配置落盘时采用了这类安全写法，二次开发新增持久化逻辑时也应遵循。

## 33.6 后台存活与电量优化

在移动设备上长期运行，最大的挑战是系统的后台回收机制。Android 的 Doze 休眠、应用待机分组、幻影进程清理以及厂商定制的省电策略，都可能在应用退到后台后冻结或杀死进程。性能调优在这类环境下与"存活能力"紧密相关：再快的响应速度，如果进程被回收导致任务中断，也毫无意义。

存活优化的第一层是合理使用唤醒锁，在执行长任务期间持有 CPU 唤醒锁，阻止设备进入深度休眠，任务结束后及时释放避免无谓耗电。第二层是把应用加入电池优化白名单、允许后台运行和自启动，尤其在国产定制系统上，需要在系统设置中明确授予无限制的后台策略。第三层是通过进程守护或开机自启，在进程异常退出或设备重启后自动拉起服务，配合轻量心跳定期检测关键进程状态，发现异常立即恢复。

电量与流量优化同样不可忽视。联网检索、流式请求、实时语音都是耗电耗流量的环节，应避免在后台无意义地轮询；定时任务尽量合并、错峰执行；实时语音这类长连接在不需要时及时断开。把存活保障与能耗控制结合起来，才能实现既稳定又不"吃电"的长期运行。

## 33.7 前端渲染性能

前端采用原生 JavaScript，没有重型框架的运行时开销，但随着对话内容、图片、代码块增多，DOM 节点持续增长仍会拖慢渲染。优化方向之一是对超长对话做虚拟渲染或分页，只渲染可视区域附近的消息，避免一次性挂载成千上万的节点。之二是代码高亮、Markdown 解析这类 CPU 密集的渲染任务做延迟处理，消息进入视口时再解析，减少初次渲染压力。

之三是合理管理图片和多媒体资源，懒加载未进入视口的图片，对已离开视口的大图释放引用，避免内存里堆积大量图像数据。之四是减少频繁的强制同步布局，批量更新 DOM、用文档片段或框架式的批量写入替代逐条操作，降低重排重绘次数。前端的流畅度直接决定用户对"性能"的第一感受，这些细节累积起来效果显著。

## 33.8 调优的测量与验证方法

任何优化都要用数据验证，避免"感觉变快了"的主观判断。网络层面，可以在日志中记录每个请求的连接耗时、首 Token 时间、总耗时，通过对比调优前后的数值确认效果。资源层面，利用系统提供的内存、CPU、I/O 监控观察峰值和趋势，重点关注长任务期间是否出现内存持续上涨（可能意味着泄漏）。存储层面，记录数据目录和备份目录的体积变化曲线，提前发现膨胀趋势。

验证优化时要警惕"优化了 A 却拖慢了 B"的副作用。例如缩短超时可能提升失败响应速度，但也会提高弱网下的误失败率；增大缓存能减少重复计算，却占用更多内存。应当在真实或接近真实的负载下、在代表性的设备上验证，而不是只在高性能环境里看理想数据。建立一组可重复的基准场景（短问答、长文档、多模态、并发混合），每次调整后跑同一组场景对比，才能让性能优化走在正确的轨道上。

# 第三十四章 故障排查与问题诊断

## 34.1 故障排查的基本原则

项目在设计上强调"如实上报错误、不静默失败"，网络层会把各类异常归一化成清晰的错误信息，日志也会保留任务执行的关键轨迹，这为故障排查提供了良好基础。排查的第一原则是先看真实错误信息，而不是凭猜测乱改。很多问题的答案就写在报错文本和日志里，跳过证据直接试错，往往越改越乱。

第二原则是分层定位，把复杂系统拆成网络、配置、鉴权、模型、存储、前端几个层次，逐层排除。先确认服务本身是否正常运行，再看请求能否到达、鉴权是否通过、模型是否可用、数据能否读写、前端是否正确渲染，每排除一层就缩小一次范围。第三原则是保留现场，遇到偶发问题时先保存日志和相关数据，再尝试重启或修改，否则重启后现场丢失，根因可能永远无法复现。第四原则是一次只改一个变量，调整一项配置后观察效果，避免多项改动叠加导致无法判断究竟哪一项起了作用。

## 34.2 服务启动类故障

服务无法启动是最基础也最常见的问题。首先检查运行环境是否满足要求：Dart SDK 版本是否符合、依赖是否完整、端口是否被占用。端口冲突时，启动会报地址已被占用的错误，此时要么释放占用端口的进程，要么通过配置更换监听端口。其次检查配置文件是否存在且格式正确，损坏的 JSON 或 YAML 会导致解析失败，项目在写入配置时采用原子替换以降低损坏概率，但手动编辑引入的语法错误仍需自行核对。

权限问题也会阻碍启动。数据目录、日志目录、备份目录如果没有读写权限，服务在初始化持久化时就会失败。在 Android 等受限环境中，还要确认应用对工作目录拥有合法访问权，且没有被系统的存储策略隔离。排查时可以查看启动日志中第一个报错的位置，最早出现的错误往往是根因，后续的连锁报错反而是结果，不要被大量红色日志淹没而忽略了最初那条关键信息。

## 34.3 鉴权与 API Key 类故障

模型调用返回 401、403 一类错误，基本指向鉴权问题。第一步核对 API Key 是否正确、是否有多余空格或换行、是否已经过期或被禁用。第二步确认 Key 对应的账号是否开通了所需模型的访问权限，有些密钥限定了可调用的模型范围，调用未授权的模型会被拒绝。第三步检查账户状态，欠费、超出配额、触发风控都可能导致鉴权或调用失败，这类问题通常会在错误信息中有所体现，需要到服务商控制台核对账单和配额。

还要注意不同服务商、不同模型的端点地址和协议差异。把 A 服务商的 Key 配到 B 服务商的端点上，或者用错了接口版本，都会鉴权失败。项目在模型配置中区分了提供方、端点、协议和密钥，排查时要逐项对应。出于安全考虑，密钥在存储时经过加密，日志中也不应明文打印，如果怀疑密钥错误，应在配置界面重新录入而不是到日志里翻找明文。

## 34.4 网络与超时类故障

网络类故障的表现多样：完全连不上、连接超时、读取超时、流式中断、DNS 解析失败等。连接超时和 DNS 失败多与网络环境有关，先确认设备本身能否访问外网，再检查是否有防火墙、代理或区域限制阻断了到模型网关的连接。在受限网络环境下，可能需要配置合法的代理或更换可达的接入点。

读取超时要结合任务类型判断。普通对话频繁读取超时，可能是网络带宽不足或网关拥塞；而长文本、深度思考、视频生成任务本身耗时长，超时往往是超时阈值设置不合理，应调大读取超时或改用异步轮询。流式输出中途断开，要排查中间代理是否缓冲或截断了长连接、移动网络是否在后台被系统切换或休眠。

重试可以缓解偶发抖动，但要警惕把"必然失败"当成"偶发抖动"反复重试。如果某个请求每次都失败，问题通常不在网络波动而在参数或权限，盲目重试只会浪费时间和费用。观察日志里同一请求的失败模式，持续失败与随机失败的处理方向完全不同。

## 34.5 模型与参数类故障

模型返回参数错误，通常是请求体不符合该模型的要求。常见原因包括：模型 ID 拼写错误或已下线、上下文长度超出模型窗口、max_tokens 设置超过模型上限、temperature 等参数超出合法区间、多模态内容发给了不支持的模型。项目的模型目录集中维护了各模型的能力参数，对话模块在拼装请求时会按模型约束做钳制，例如把过长的时长、过大的输出限制收敛到合法范围，降低被网关拒单的概率。

排查这类问题时，先在日志中定位被拒请求的实际参数，与模型目录中的约束逐项比对。如果是上下文超长，应减少历史轮次或压缩检索内容；如果是能力不匹配，例如把图片发给纯文本模型，应改选支持视觉的模型。模型版本更新后，旧 ID 可能被废弃，需要及时同步模型目录，这也是为什么项目把模型清单集中管理、便于统一维护。

## 34.6 数据与存储类故障

数据类故障包括历史丢失、配置重置、备份失败、索引异常等。历史或配置异常时，优先检查数据目录的文件是否完整、磁盘空间是否充足。空间耗尽会导致写入失败，进而出现看似"数据丢失"的现象，实际上是新内容写不进去。备份失败尤其要关注剩余空间，打包整个数据目录需要一定的临时空间，空间不足会在打包中途报错。

如果数据文件意外损坏，不要在原文件上反复尝试，应先保留现场，再用最近的备份恢复。这也是备份策略的价值所在——定期、异地、多版本的备份，是应对存储故障最可靠的兜底。全文索引异常时，可以通过重建索引修复，索引本身是可从原始数据重新生成的派生数据，重建不会损失原始内容。

跨设备或重装后的恢复，要注意数据目录的路径和权限一致性，把备份还原到项目期望的位置并授予正确权限，服务才能正常加载。加密存储的数据与设备或密钥环境相关，迁移时要确保解密所需的条件一并具备，否则可能出现数据还在却无法解密的情况。

## 34.7 前端与交互类故障

前端问题的排查要区分是数据问题还是渲染问题。如果接口返回正常但界面不显示，多半是前端渲染逻辑或静态资源加载的问题；如果接口本身报错，则应回到后端和网络层排查。浏览器的开发者工具是前端排查的利器：网络面板看请求状态和返回内容，控制台看 JavaScript 报错，元素面板检查 DOM 结构。

多语言切换异常时，先确认对应的语言文件是否完整、键名是否与源语言一致，缺失的键会回退到源语言或显示键名本身。实时语音、录音、摄像头这类能力依赖浏览器权限和设备硬件，无法使用时先检查权限授予情况和硬件占用状态。缓存导致的旧界面问题，可以通过强制刷新或清理缓存验证，项目更新前端资源后，合理设置缓存策略能减少用户拿到旧版本的概率。

## 34.8 性能退化与进程被杀的排查

如果发现服务越用越慢、频繁卡顿或后台任务经常中断，要从资源和系统策略两方面排查。资源方面，观察内存是否随时间持续上涨（潜在泄漏）、数据目录是否过度膨胀、是否有大量并发任务堆积。系统策略方面，重点排查应用是否被移出电池优化白名单、唤醒锁是否失效、是否触发了幻影进程清理或厂商省电冻结。

进程在后台静默死亡是移动环境的典型问题，且容易被误判成程序逻辑错误。排查时要结合系统日志判断死因：是内存不足被回收、Doze 休眠被冻结，还是厂商省电策略主动清理。确认是系统回收后，应对症下药地恢复白名单、唤醒锁、自启动和进程守护，而不是去改业务代码。项目要求把这类中断作为显式事件记录，正是为了避免"任务其实已死却看似在运行"的静默失败。

## 34.9 建立系统化的诊断流程

把上述经验沉淀成一套可复用的诊断流程，遇到问题时按图索骥，可以显著提升排查效率。第一步，复现并记录问题，明确触发条件和错误现象；第二步，查看日志和真实报错，定位最早的异常点；第三步，分层排查，从服务存活、网络连通、鉴权、模型参数、数据存储到前端渲染逐层缩小范围；第四步，基于证据形成假设，一次改动一个变量验证；第五步，修复后回归测试，并把根因和解决方案记录下来，形成团队的故障知识库。

对于难以稳定复现的偶发问题，要善用日志和监控捕捉现场，必要时临时增强关键路径的日志粒度，在问题再次发生时拿到足够信息。保持冷静、尊重证据、拒绝猜测式乱改，是高效故障排查最重要的素养。项目"如实上报、全链路留痕"的设计，正是为了让每一次故障都有迹可循、有证可查。

# 第三十五章 安全设计与隐私保护

## 35.1 安全设计的整体观

本项目处理的是高度敏感的数据：模型服务商的 API Key、用户的对话内容、上传的文件与多媒体、账号与配置信息。一旦泄露，可能造成密钥被盗用、隐私内容外泄、财产损失等严重后果。因此安全不是某个单一模块的职责，而是贯穿网络传输、本地存储、密钥管理、访问控制、文件处理、日志审计各个环节的系统工程。本章结合项目的真实实现，阐述各层安全机制的原理与使用要点。

安全设计遵循几条基本原则。第一是最小权限，任何模块、任何接口只拥有完成其职责所必需的最小权限，不授予多余的访问能力。第二是纵深防御，不依赖单一防线，而是在传输、存储、访问、审计多层分别设防，即使一层被突破，其他层仍能提供保护。第三是默认安全，开箱即用的默认配置就应当是安全的，而不是要求用户手动开启一堆安全选项。第四是敏感数据最小暴露，密钥等机密在存储、日志、错误信息中都不明文出现，降低泄露面。

## 35.2 传输层安全

客户端到服务端、服务端到模型网关的通信都应基于 HTTPS/TLS 加密，防止数据在网络链路上被窃听或篡改。项目的网络层默认走加密连接，部署时应确保证书有效、协议版本安全，避免为了省事降级到明文 HTTP，尤其是在公网暴露服务的场景下，明文传输等于把 API Key 和对话内容直接暴露给链路上的任何观察者。

如果部署中使用了反向代理或 CDN，要保证加密的连续性：用户到代理一段加密，代理到后端服务一段也应加密或走受信任的内部网络，避免在代理处形成明文"缺口"。同时要关注证书的有效期与自动续期，证书过期会导致所有请求失败，是生产环境常见的事故来源。对于 SSE 流式长连接，同样要确保传输层加密且中间设备不会因为超时而切断连接。

## 35.3 本地加密存储

项目对敏感配置采用专门的加密模块保护，核心是经过认证的加密算法。`ds_crypto` 基于 AES-GCM 这类带认证的加密方案：AES 负责数据加密，GCM 模式同时提供完整性校验，使得密文一旦被篡改，解密阶段就能检测出来，而不会输出被污染的数据。相比只加密不校验的方案，认证加密能有效抵御密文篡改攻击。

加密密钥的管理是安全的命门。再强的算法，如果密钥硬编码在代码里或明文存放在配置文件中，也形同虚设。项目通过系统级的密钥派生或安全存储机制生成和保管密钥，避免把密钥直接写死。加密后的配置以密文形式落盘，即使设备丢失、存储介质被取出，攻击者在没有密钥的情况下也无法还原出 API Key 等机密。

哈希算法用于不需要还原、只需校验的场景。例如对敏感标识做摘要、校验文件完整性时，使用 SHA-256 这类抗碰撞的哈希函数。哈希是单向的，无法从摘要反推原文，适合存储用于比对而非解密的信息。理解加密与哈希的区别很重要：需要还原的机密用可逆的认证加密，只需校验的场景用单向哈希，二者各司其职，不能混用。

## 35.4 密钥与凭证管理

API Key 是整个系统中价值最高的凭证，拿到它就等于拿到了账户的调用额度。管理上要做到几点：其一，录入后即以密文存储，界面和日志中默认掩码显示，需要时只展示末位用于辨认，绝不完整回显。其二，错误信息和调试日志中禁止打印完整密钥，项目在网络层和日志层对敏感字段做了脱敏处理，防止密钥随报错或日志泄露。其三，不同环境、不同用途使用独立的密钥，避免一个密钥泄露波及全部业务，也便于按密钥维度做用量统计和权限隔离。

其四，建立密钥轮换机制，定期或在怀疑泄露时更换密钥，旧密钥及时吊销。其五，在服务商侧为密钥设置合理的权限边界和用量上限，遵循最小权限原则，即使某个密钥泄露，攻击者能调用的模型、能消耗的额度也受到限制。用户在二次开发时尤其要避免把密钥硬编码进前端代码或提交到代码仓库——前端代码对用户可见，提交到仓库则可能被公开检索，这两种都是高频的密钥泄露途径。

## 35.5 访问控制与接口防护

对于通过 HTTP 暴露的接口，访问控制决定了谁能调用什么。项目在服务层对敏感操作设置了鉴权与校验，部署到公网时还应在前置代理层加强防护：启用身份认证、限制可访问来源、对管理类接口做更严格的权限控制。不要把具备文件读写、系统操作、模型调用能力的接口毫无防护地暴露到公网，否则可能被未授权访问者利用。

请求体大小限制是一类容易被忽视的防护。限制单次请求的体积，可以防止超大 payload 耗尽内存和带宽，缓解拒绝服务攻击。文件上传接口要校验文件类型、大小和路径，防止恶意文件被上传到可执行目录，或通过构造特殊文件名实现目录穿越。项目的文件管理模块对路径做了规范化和边界校验，确保所有操作被限制在允许的目录内，避免 `../` 一类的路径逃逸攻击。

## 35.6 文件处理与路径安全

文件管理功能天然带有风险，因为它直接操作真实的文件系统。安全的文件处理首先要做路径校验：把用户传入的相对路径规范化后，确认其最终指向仍在允许的根目录之内，任何试图跳出根目录的请求都应被拒绝。其次是区分读写权限，对删除、覆盖、移动这类破坏性操作增加确认或权限校验，避免误操作或恶意操作造成不可逆损失。

上传文件时要警惕可执行内容，不应允许用户把脚本、可执行程序写入会被服务端执行的位置。下载和分享文件时要确认访问范围，避免敏感文件被未授权获取。临时文件应使用不可预测的名称、存放在受控目录，并在使用后及时清理，防止临时文件堆积或被其他请求越权读取。这些措施共同构成文件层面的安全边界，让便利的文件管理不至于成为系统的突破口。

## 35.7 日志审计与隐私

日志是排查问题和安全审计的重要依据，但也可能成为隐私泄露的渠道。项目在日志设计上把握"记录足够排查的信息、但不记录敏感明文"的平衡：会记录请求的时间、类型、状态、耗时、错误类别等运维所需信息，但对 API Key、完整对话内容、密码等敏感数据做脱敏或不记录。这样既保留了可观测性，又避免日志本身成为机密的集合体。

审计能力让安全事件可追溯。关键操作——尤其是登录、配置变更、密钥修改、文件删除、备份恢复这类高风险动作——应当留下操作记录，包含时间、来源、动作和结果，一旦出现异常可以回溯定位。用户也应意识到对话数据的隐私属性：在共享设备或公共环境使用后，注意会话的清理；涉及高度机密的信息，应谨慎决定是否输入到云端模型，因为数据会离开本地、发送到服务商进行推理。

## 35.8 依赖与供应链安全

项目虽然在后端追求零依赖、减少供应链风险，但任何引入的第三方库、前端资源、自动化脚本都构成供应链的一部分。依赖管理上要使用来源可信、维护活跃的组件，定期更新以修补已知漏洞，避免使用无人维护或来源不明的包。前端引用第三方资源时尽量走可信 CDN 并配合完整性校验，防止资源被篡改后注入恶意代码。

自动化脚本和插件是能力的扩展点，也是风险的扩展点。安装第三方脚本或插件前应审查其行为，确认没有偷偷外传密钥、读取敏感文件、执行危险命令的逻辑。遵循最小权限运行脚本，不随意授予过高的系统权限。供应链安全的核心是信任管理——清楚每一个引入组件的来源和行为，把信任建立在可验证的基础上，而不是盲目地"拿来就用"。

## 35.9 用户侧安全实践清单

最后汇总一份面向使用者的安全实践清单，便于逐项核对。第一，所有通信走 HTTPS，公网部署务必加身份认证。第二，API Key 只通过正规界面录入，依赖系统加密存储，绝不写进前端或仓库。第三，为密钥设置用量上限和最小权限，定期轮换。第四，及时更新系统、依赖和项目版本，修补已知漏洞。第五，谨慎处理文件上传与共享，理解路径校验的保护作用。第六，关注日志中的异常访问和用量突增，配置费用告警。第七，共享环境注意会话与隐私清理，敏感信息谨慎上云。第八，备份数据加密保存、异地存放，备份本身也要纳入安全管理。把这份清单落到日常使用中，才能让项目在发挥强大能力的同时，把安全风险控制在可接受的范围内。

# 第三十六章 常见问题 FAQ

本章把部署、配置、使用过程中高频出现的问题集中解答，问题按主题分组，便于快速检索。每个解答都结合前面章节的真实机制，遇到具体问题时既知其然也知其所以然。

## 36.1 部署与启动类

**问：启动时提示端口被占用怎么办？**
答：说明配置的监听端口已被其他进程使用。可以先查出占用端口的进程并结束它，也可以在配置中更换一个空闲端口。修改后重新启动即可。若在同一台机器上跑了多个实例，要为每个实例分配不同端口。

**问：服务启动后无法访问，浏览器一直转圈？**
答：按层排查。先确认服务进程确实在运行、监听了正确的地址和端口；再检查防火墙或安全组是否放行该端口；如果部署在远程设备，确认访问的是正确的 IP 和端口；本地访问可用回环地址，远程访问则要用设备的实际网络地址。HTTPS 场景还要确认证书和访问协议匹配。

**问：升级版本后启动报错？**
答：多为配置或数据结构版本不一致导致。先查看启动日志的首个报错，确认是否缺少新增配置项或数据格式需要迁移。升级前按规范做好备份，出现问题可用备份回滚，再参照新版本文档补齐配置。不要在没有备份的情况下直接覆盖数据目录。

**问：在手机上运行，后台一段时间服务就停了？**
答：这是系统后台回收导致的，不是程序崩溃。需要把应用加入电池优化白名单、允许后台运行和自启动、持有唤醒锁，并配置进程守护或开机自启。具体可参考第三十三章的后台存活部分，国产定制系统通常还要在系统设置里手动授予无限制后台策略。

## 36.2 模型与密钥类

**问：调用模型返回 401 或 403？**
答：属于鉴权失败。核对 API Key 是否正确、有无多余空格、是否过期或被禁用；确认该密钥已开通目标模型的调用权限；检查账户是否欠费、超配额或被风控；还要确认端点地址、协议与密钥所属服务商一致。逐项排查后基本都能定位。

**问：为什么我选的模型在下拉列表里找不到？**
答：前端模型列表由后端模型目录动态生成。先确认模型目录中确实配置了该模型且分类正确，再确认当前密钥拥有该模型权限，最后刷新前端缓存重新拉取列表。新增模型后若列表未更新，多为前端缓存所致，强制刷新即可。

**问：视频生成提示时长或参数不合法？**
答：不同视频模型支持的时长、分辨率范围不同。系统会按所选模型的能力对参数做钳制，例如较新的模型支持更长时长，老模型有更严格的上限。若仍报错，核对请求参数是否落在该模型的合法区间，必要时降低时长或分辨率。模型目录中维护了各模型的具体约束。

**问：上下文太长导致请求失败？**
答：输入超过了模型的上下文窗口。可以减少保留的历史轮次、压缩较早的对话、裁剪联网检索注入的内容，或改用支持更长上下文的模型。项目对历史做了分层管理，合理设置历史上限能在连贯对话和窗口限制之间取得平衡。

## 36.3 对话与生成类

**问：回答出现"幻觉"、编造不存在的信息怎么办？**
答：大语言模型本质是概率生成，存在幻觉是固有特性。缓解方法包括：需要事实准确性时开启联网检索，让回答基于实时资料；在提示词中要求模型对不确定内容明确说明、给出依据；把温度参数调低，降低发散程度；对关键事实人工复核。项目的联网插件和较低温度的默认配置，正是为了抑制幻觉。

**问：流式输出一卡一卡、不是逐字出现？**
答：可能是中间代理缓冲了 SSE 数据，使流式退化成批量返回；也可能是网络抖动或模型本身生成较慢。先检查反向代理是否关闭了响应缓冲、是否放行长连接；弱网下可观察首 Token 时间是否正常，若首字很快只是后续波动，多为网络因素。

**问：深度思考模式比普通模式慢很多，正常吗？**
答：正常。深度思考会让模型先生成完整的推理链再给出结论，输出的 Token 更多、耗时更长，费用也相应增加。适合复杂推理、多步规划的难题；简单问答用普通模式即可，兼顾速度和成本。

**问：多模态图片识别效果不理想？**
答：先确认使用的是支持视觉的模型；再检查图片是否清晰、分辨率是否合适，过大的图会被压缩、过小的图细节不足；提问时尽量明确需要识别的内容和目标。复杂图表、多图对比可以分步骤提问，帮助模型聚焦。

## 36.4 联网插件与计费类

**问：什么情况下会触发付费的联网插件？**
答：只有在明确需要对应信源、且该信源开关处于开启状态时才会调用。普通问题默认走基础检索，不会主动触发付费信源。每次成功调用付费插件都会在回答中标注信源和费用，便于和后台日志逐笔对账。若对应开关关闭，系统不会偷偷调用，而是提示信源未开启。

**问：Token 费用是怎么计算的？为什么每次费用不一样？**
答：费用由输入 Token 和输出 Token 两部分组成，单价不同。输入侧包含系统提示词、历史对话、检索内容、工具返回等所有送入模型的文本，输出侧是模型生成的内容。对话轮次越多、注入的资料越长、回答越长，消耗就越高。项目的用量统计会拆分记录输入输出，可据此分析成本来源。

**问：如何避免自动化任务产生意外高额账单？**
答：为自动化脚本设置调用频率上限、单次和累计费用阈值、失败熔断，避免异常重试或逻辑死循环持续调用付费接口。配合用量统计和费用告警，在达到阈值时及时通知或自动暂停。无人值守任务尤其要先小规模验证逻辑，确认不会失控后再放开运行。

**问：联网检索没有返回想要的结果？**
答：检索质量与关键词、信源覆盖度有关。可以优化提问中的关键词、把问题描述得更具体；需要权威词条时使用百科类信源，需要时效资讯时使用图文类信源。若所有信源都无匹配，系统会如实告知未检索到内容，而不是编造答案。

## 36.5 数据、备份与安全类

**问：我的对话历史会丢失吗？**
答：历史会持久化到数据目录，正常退出和异常中断后一般都能保留。但磁盘损坏、误删、设备故障仍可能导致丢失，因此应定期使用备份功能，并把备份异地保存。开启自动备份、保留多个历史版本，是最稳妥的保护方式。

**问：备份恢复后数据对不上？**
答：先确认备份包完整、还原到了正确的数据目录且权限正确。加密数据的还原还需具备解密条件。恢复前建议先备份当前状态，避免还原操作覆盖掉新数据。若备份包本身损坏，尝试使用更早的版本恢复。

**问：API Key 会不会被明文看到？**
答：密钥经认证加密后密文存储，界面默认掩码、日志脱敏，正常使用中不会明文暴露。但用户自身也要避免把密钥写进前端代码、提交到代码仓库或在不可信环境录入，形成人为泄露通道。

**问：文件管理功能安全吗，会不会越权访问？**
答：文件模块对路径做了规范化和边界校验，所有操作被限制在允许的目录内，能抵御目录穿越尝试。删除、覆盖等破坏性操作有相应的确认或权限控制。使用者仍应谨慎处理重要文件，避免误删，并通过备份兜底。

## 36.6 多语言与前端类

**问：切换语言后部分文字还是原来的语言？**
答：通常是对应语言文件缺少该键名的翻译，系统回退到了源语言。补齐该语言文件中缺失的键值即可。新增界面文案时，要同步在各语言文件中添加对应翻译，保持键名一致。

**问：实时语音或录音功能用不了？**
答：这类能力依赖浏览器麦克风权限和设备硬件。先在浏览器设置中确认已授予麦克风权限、没有被其他应用占用；再检查网络是否支持长连接。部分浏览器对非安全上下文（非 HTTPS）会限制媒体能力，部署时应使用 HTTPS。

**问：界面显示异常、像是旧版本？**
答：多为浏览器缓存了旧的前端资源。强制刷新或清理缓存后重新加载即可。部署更新时合理设置静态资源的缓存策略，能减少用户拿到旧版本的概率。若伴随控制台报错，则按报错信息排查具体脚本。

## 36.7 自动化与运维类

**问：ADB 自动化连接不稳定、经常断开？**
答：无线调试受网络波动和设备休眠影响。应配置自动重连逻辑，定期检测连接状态，断开后主动恢复；同时保证设备和运行环境在同一可达网络、应用持有必要的后台权限。配合进程守护，让自动化服务在异常退出后自动拉起。

**问：定时任务有时不执行？**
答：在移动设备上，多与后台休眠或省电策略有关。确认应用在电池优化白名单内、持有唤醒锁、允许自启动。任务调度也要考虑设备重启后的恢复，通过开机自启让任务在重启后重新生效。

**问：日志越来越大怎么办？**
答：配置日志轮转，按大小或时间切分并保留有限份数，避免单个日志文件无限膨胀。定期归档历史日志到其他存储，既保留排查所需的历史信息，又不让日志占满工作磁盘。

# 第三十七章 结语与生态展望

## 37.1 项目的工程价值回顾

通读全文可以看到，这个项目并不是简单地把大模型接口包装成一个聊天窗口，而是围绕"让大模型真正能稳定、安全、低成本地干活"这一目标，构建了一整套完整的工程体系。后端用 Dart 以零依赖的方式实现了 HTTP 服务、模型路由、加密存储、备份恢复、用量统计、全文搜索、文件管理等核心能力；前端用原生 JavaScript 实现了流畅的对话、多模态、实时语音、多语言等交互；再辅以 Python 和 Shell 自动化脚本，形成了可在资源受限的移动环境中长期稳定运行的实用系统。

这套体系的可贵之处在于它的"真实"和"克制"。真实，体现在每一个功能都对应实际的代码实现，错误如实上报、任务全程留痕、数据可备份可恢复，不做表面文章；克制，体现在零依赖的后端、按需调用的付费插件、严格的安全边界和成本控制，不堆砌华而不实的能力。正是这种务实的工程取向，让项目能够在复杂多变的真实环境里持续可靠地交付价值。

## 37.2 大模型能力与工程框架的关系

理解这个项目，关键是理解"模型"与"框架"的分工。大模型提供的是基础智能——语言理解、内容生成、推理规划、多模态感知，但裸模型本身并不能直接成为好用的产品。它需要一个运行框架（Harness）来补齐工程能力：管理会话与记忆、对接工具与联网、控制权限与安全、统计用量与费用、处理并发与错误、适配多语言与多端交互。模型决定了智能的上限，框架决定了能力落地的下限和稳定性。

这也解释了为什么同一个模型，在不同系统里的实际体验差异巨大。优秀的框架能够通过合理的上下文管理抑制幻觉、通过工具调用补足实时性、通过参数钳制避免报错、通过加密和审计保障安全、通过用量统计控制成本。本项目所做的，正是把这些"让模型好用、可靠、可控"的工程环节逐一夯实，让强大的模型能力真正转化为可托付的生产力。

## 37.3 豆包生态的持续演进

在国产大模型生态中，豆包系列凭借高性价比、长上下文、原生多模态和稳定的工具调用能力，成为这类工程框架非常合适的能力底座。从轻量的 Seed Lite 系列到旗舰模型，从文本对话到视觉理解、语音交互、视频生成，豆包提供了覆盖多场景的完整模型矩阵，且定价友好、接入规范统一，便于在一个系统内按任务复杂度分层调度，兼顾效果与成本。

随着模型能力持续演进，框架也需要保持同步：新模型发布时及时更新模型目录、适配新的参数与能力边界；多模态能力增强时扩展相应的处理流水线；智能体自主执行能力提升时，同步强化权限分级、沙箱隔离和全链路审计，防止"能力越强、风险越大"。模型与框架这种相互促进、共同迭代的关系，正是人工智能应用走向成熟的常态。

## 37.4 给使用者的最后建议

如果你是这个项目的使用者，希望这份文档能帮你把系统用得更顺、更省、更安全。记住几条贯穿全文的核心建议：第一，善用模型分层，简单任务用轻量模型、复杂任务才上旗舰，配合合理的历史管理控制 Token 成本；第二，尊重付费插件的触发规则，按需调用、逐笔对账，用自动化时设好费用阈值；第三，把备份和安全当成习惯，定期备份、异地保存、管好密钥、最小授权；第四，在移动环境重视后台存活，白名单、唤醒锁、进程守护缺一不可；第五，遇到问题先看真实日志、分层定位、一次只改一个变量，用证据而不是猜测驱动排查。

如果你是二次开发者，建议延续项目已有的工程规范：保持后端的零依赖和异步风格、复用统一的网络与加密模块、把模型能力集中在模型目录管理、新增文案同步补齐多语言、所有持久化采用原子写入、敏感信息绝不硬编码。在既有架构的约束内扩展，新功能才能与系统无缝融合，而不是埋下维护隐患。

## 附录 A：术语表

- **大语言模型（LLM）**：基于海量文本预训练、能理解和生成自然语言的深度学习模型。
- **Token**：模型处理文本的基本计量单位，中文通常一个字或词对应若干 Token，计费按输入输出 Token 数计算。
- **上下文窗口**：模型单次请求能处理的最大 Token 总量，包含输入与输出。
- **温度（temperature）**：控制生成随机性的参数，值越低越确定保守，越高越发散。
- **幻觉**：模型生成看似合理但与事实不符内容的现象。
- **思考链（CoT）**：模型显式输出中间推理步骤以提升复杂任务准确率的机制。
- **智能体（Agent）**：能自主感知、规划、调用工具并执行任务的 AI 形态，模型加运行框架构成智能体。
- **SSE**：服务器推送事件，实现流式输出的一种机制，让内容逐段返回。
- **多模态**：模型处理文本、图片、音频、视频等多种数据类型的能力。
- **AES-GCM**：带完整性认证的对称加密方案，兼顾保密性与防篡改。
- **Doze**：安卓系统的深度休眠省电机制，会限制后台应用。
- **唤醒锁**：阻止设备进入深度休眠、保证后台任务持续运行的机制。

# 第三十八章 端到端实战演练

本章用一个完整的实战场景，把前面分散在各章的能力串联起来，帮助你建立从部署到日常使用、再到运维保障的整体认知。场景设定为：在一台安卓设备上，通过 Termux 环境运行本系统，接入豆包大模型，搭建一个支持对话、联网、多模态、多语言，并能长期稳定后台运行的个人 AI 助手。

## 38.1 第一步：环境准备与服务启动

首先确认设备已安装符合版本要求的 Dart 运行环境，工作目录位于 Termux 的家目录下。拉取项目代码后，先检查数据目录、日志目录、备份目录是否具备读写权限，避免服务在初始化持久化时因权限不足而启动失败。随后执行启动命令，观察启动日志：正常情况下会依次完成配置加载、加密模块初始化、HTTP 服务监听、模型目录装载。如果日志出现端口占用，就更换端口或释放占用进程；如果出现配置解析错误，就核对配置文件格式。确认服务监听在预期地址和端口后，用浏览器访问对应入口，看到前端界面即代表启动成功。

这一步的关键是"看日志、对报错"，而不是盲目反复重启。启动阶段的错误通常非常明确，顺着第一条报错定位，往往一次就能解决。

## 38.2 第二步：接入豆包模型

进入模型配置界面，选择豆包作为提供方，填入从火山引擎控制台获取的 API Key。录入时注意不要带多余空格，密钥保存后会以密文形式落盘，界面只显示掩码。接着填写对应的端点地址和协议，确保与密钥所属服务商一致。然后在模型目录中确认需要使用的豆包模型已正确配置，包括文本对话模型、视觉模型、视频模型等，并核对各自的上下文窗口、最大输出、时长分辨率等能力参数。

配置完成后做一次最小化验证：发送一句简单的对话，观察是否正常流式返回。如果返回鉴权错误，回到第三十六章的鉴权排查清单逐项核对；如果正常返回，再测试联网检索、图片理解等扩展能力，确认密钥权限覆盖了所需模型。建议为这个密钥设置用量上限，遵循最小权限原则，为后续成本控制打下基础。

## 38.3 第三步：配置联网与多语言

根据实际需要配置联网信源。理解并遵守付费插件的触发规则：只有明确需要对应信源、且开关开启时才调用，普通问题走基础检索。这样既能在需要权威词条或时效资讯时获得高质量结果，又能避免不必要的费用。每次付费调用都会标注信源和费用，可与后台日志对账。

多语言方面，在界面切换到熟悉的语言，验证各模块文案是否完整。如果发现个别文案回退到源语言，说明对应语言文件缺少键值，补齐翻译即可。对于多语言使用者，这套机制让同一套后端能力可以服务不同语言偏好的用户，而无需为每种语言单独部署。

## 38.4 第四步：验证多模态与工具能力

依次验证图片理解、语音合成、实时语音、视频生成等能力。图片理解选择支持视觉的模型，上传一张清晰图片并明确提问；语音合成长文本时，系统会自动做切分处理，避免单次请求超长；实时语音需要授予浏览器麦克风权限并在 HTTPS 环境下使用；视频生成则按所选模型的时长、分辨率约束设置参数，较新的模型支持更长时长，老模型会被自动钳制到合法范围。

工具模式下，可以观察模型如何把复杂目标拆解为步骤、按需调用工具、根据中间结果调整路径。这是智能体区别于普通聊天机器人的核心。使用中体会思考链带来的推理透明度，也注意其成本和延迟高于普通模式，按任务复杂度合理选择。

## 38.5 第五步：配置备份与安全

进入备份设置，指定备份目录并配置自动备份策略，建议把备份目录与活跃数据目录分开，有条件时异地保存，保留多个历史版本。手动触发一次备份，确认备份包完整生成，再演练一次恢复流程，确保在需要时真的能还原——没有验证过恢复的备份等于没有备份。

安全方面逐项核对实践清单：确认通信走 HTTPS、密钥加密存储且掩码显示、文件管理路径校验生效、日志不含敏感明文、密钥设置了用量上限和最小权限。理解加密与哈希的分工、认证加密防篡改的原理，让安全配置建立在理解而非机械操作之上。

## 38.6 第六步：保障长期稳定运行

这是移动环境下最关键的一步。把应用加入电池优化白名单，允许后台运行、自启动，配置无限制的后台省电策略；在长任务期间持有唤醒锁，阻止设备深度休眠；配置进程守护或开机自启，让服务在崩溃或设备重启后自动拉起；建立轻量心跳，定期检测关键进程和连接状态，发现异常立即恢复并记录中断事件。

同时配置用量与费用告警，给自动化任务加上频率上限、费用阈值和失败熔断，防止无人值守时失控产生高额账单。定期巡检日志、监控数据目录和备份目录的体积、做日志轮转，形成可持续的运维节奏。完成这些配置后，系统才真正具备在真实移动环境中长期、稳定、可托付运行的能力。
